# MediaCli Desktop UI/UX 优化方案审查报告

- **审查对象**：`docs/DESKTOP-UIUX-OPTIMIZATION-PLAN-20260925.md`
- **审查时间**：2026-09-25 14:27:22（GMT+8）
- **审查基线**：当前工作区代码，包含尚未提交的 Desktop UI 改动
- **审查范围**：产品流程、信息架构、状态与并发安全、架构影响、验证策略；不纠缠文字和代码行号
- **结论**：**方向正确，但需重大修订后再实施**

---

## 1. 总体评价

方案抓住了当前 Desktop 最明显的产品问题：把底层 `plan` 概念直接暴露给用户，导致主流程被“生成计划 → 开始转码”这类技术步骤割裂。这个判断是成立的。

真正应借鉴 ShanaEncoder / HandBrake 的并不是“添加后立即无检查地执行”，而是：

1. 用户配置的是输入、预设、输出位置和本次运行范围；
2. 系统内部仍需完成媒体探测、参数计算、目标路径检查和命令构建；
3. 这些内部步骤不应要求普通用户逐项点击“生成计划”；
4. 用户点击一次明确的“开始转码”，系统自动完成准备并执行；
5. 执行完成后可以立即播放、定位和检查产物。

因此，方案的核心方向可以保留，但应从“解禁按钮并串联两个前端调用”升级为：

> **把 plan 从用户工作流概念降级为内部的 preflight / preparation 阶段，并为用户提供持续可见、可取消、可恢复的执行反馈。**

当前版本不能原样实施。主要原因不是细节，而是存在任务选择范围、重新规划、并发状态和输出安全方面的隐患；“全部是 Renderer 改动、零架构风险”的判断也不成立。

### 建议的决策

| 方案项 | 结论 | 调整方向 |
|---|---|---|
| 取消显式“生成计划”门槛 | 采纳，但需重构 | 使用单一的原子化“准备并开始”命令 |
| 输出位置常驻可见 | 采纳 | 只保留一个事实源，并显示真实最终路径语义 |
| 底部源/目标结构化对比 | 有条件采纳 | 先补公共数据契约；默认使用紧凑差异摘要，详情按需展开 |
| 完成后播放源/产物 | 采纳 | 放入行操作或溢出菜单，处理失败反馈和源文件已清理场景 |
| 顶栏与日志减法 | 部分采纳 | 移除重复硬件信息与高频参数日志；完成动作不应放进本轮 |
| 系统休眠/关闭应用 | 暂缓 | 需要主进程能力、持久化和严格终态条件，不属于纯 UI 优化 |

## 2. 方案中值得保留的判断

### 2.1 “生成计划”不应是普通用户必须理解的主流程步骤

当前界面把内部实现阶段提升成了和“开始转码”并列的一级操作。用户真正关心的是：

- 哪些文件会处理；
- 使用什么预设；
- 产物写到哪里；
- 是否会覆盖或删除源文件；
- 点击开始后当前系统在做什么。

“计划是否已经生成”只应作为内部状态和诊断信息。方案取消该阻断的方向正确。

### 2.2 输出位置应在执行前持续可见

HandBrake 官方流程也明确要求用户在开始前确认 Destination。输出位置是批量文件工具的高风险全局配置，不应隐藏在侧栏滚动内容中。

方案把输出策略提升到主任务区的判断正确，但不应在侧栏和底栏各放一份可编辑控件。应使用一个共享控件或“摘要 + 更改”入口。

### 2.3 完成后直接播放产物是高价值闭环

`openPath` 已通过 preload 暴露，主进程也已有路径白名单校验。成功后直接调用系统默认应用回放，能显著缩短验收路径，适合纳入近期实施。

不过不建议在表格每一行长期占用两个播放按钮。更合适的是：

- 行单击：聚焦任务；
- 行双击 / 详情按钮：打开检查器；
- 右键或更多菜单：播放源文件、播放产物、定位文件、复制路径、查看错误。

### 2.4 日志和静态硬件信息应做减法

连续拖动 CRF 滑块产生大量 INFO 审计记录，确实会淹没 FFmpeg 错误。删除高频参数监听日志是合理优化。

CPU 核数和静态内存快照也不应常驻占用顶栏。但当前 `StatusBar` 还重复展示了 CPU、内存和硬件层；只删除 `HeaderBar` 的胶囊并不能完成整体减法，应统一收敛到一个位置。

### 2.5 “极简”方向正确，但应以任务优先级衡量，而不是以控件数量衡量

目标规格、完成状态、输出位置和主操作都是高频高价值信息；预设细节、命令、硬件矩阵和完成后的电源动作属于低频信息。真正有效的减法是把低频信息移出主视线，而不是把所有功能都压缩成一行后继续堆在顶栏。

## 3. 必须先修正的关键问题

## P0-1：一键自动重规划会破坏用户明确取消勾选的任务范围

这是当前方案最严重的安全问题。

当前执行链路存在以下组合行为：

1. 用户可以逐行取消勾选，表示“本次不要处理这些文件”；
2. `App.vue` 的 `startExecution()` 在选择为空时向主进程传 `undefined`；
3. 主进程把 `undefined` 解释为“执行全部任务”；
4. `planStore.setPlan()` 每次生成新计划时都会默认全选；
5. 方案又要求在 `STALE` 或存在 staged 任务时自动生成计划后直接执行。

由此会产生如下危险场景：

> 批次有 100 个文件，用户取消勾选其中 20 个；随后调整一次分辨率并点击“开始转码”。自动重规划恢复全选，随后 100 个文件全部进入执行范围。

即使当前按钮尚未解禁，这个问题也已经存在；方案把开始按钮改成“只要有任务就永久可用”会进一步放大它。

### 建议

- “未选择任何任务”必须表示**不执行**，绝不能回退为“执行全部”；
- 开始按钮的可用条件至少应为 `selectedIds.size > 0`；
- `startExecution` 必须始终显式传递任务 ID，禁止用 `undefined` 隐式表达全选；
- 自动重规划后，按规范化源文件路径恢复用户原有选择，而不是按每次重建的 task ID 恢复；
- 新加入的任务是否自动勾选应有明确规则，建议默认加入当前批次并勾选，但不得重置用户对旧任务的取消决定。

## P0-2：任务列表不是重新规划的唯一事实源，移除任务可能在重规划后复活

当前行移除只修改 `planStore.tasks`，而 `createPlan()` 会重新扫描 `configStore.inputs`。因此：

- 对单文件输入，从表格移除后再次自动规划，该文件可能重新出现；
- 对目录输入，移除目录中的某个任务后再次规划，该任务会被重新扫描回来；
- 一键开始把“移除”从无效的列表装饰变成了不可靠的安全操作。

在显式两阶段流程下，这个问题容易被用户规避；在一键自动重规划下会变成常态。

### 建议

建立唯一的 canonical queue：

- 队列以规范化媒体源路径为稳定身份；
- 表格行、勾选、移除、焦点均引用同一队列实体；
- `configStore.inputs` 只负责待扫描入口，不应和已展开的任务列表形成两个可同时编辑的事实源；
- 重规划只更新已有任务的派生信息，不重新引入用户已移除的源文件；
- 目录展开后，将目录展开结果固化进队列；目录本身可保留为来源说明，但不再在每次运行时重新扫描。

## P0-3：仅用“是否有任务、是否运行中”决定开始按钮可用是不安全的

方案提出只要 `tasks.length > 0` 且不是 `RUNNING/STOPPING` 就永久可点击。这会遗漏至少以下状态：

- `PLANNING`；
- 输入仍在 staging / ffprobe；
- 用户已取消全部勾选；
- 所有任务已完成、跳过或失败；
- 上一次规划失败，主进程已没有 active plan；
- 任务仍显示在 Renderer，但主进程计划已被清理或替换；
- 新文件正在导入，旧计划已经开始运行。

### 建议

将“会话阶段”“计划是否最新”“输入是否正在导入”“是否有可执行选择”拆成独立状态，而不是继续把它们挤进 `RunnerState`：

```text
sessionPhase: idle | ingesting | preparing | running | stopping | terminal
planState: none | current | stale | failed
selection: selected paths / task count
inputState: pending ingestion count
```

开始按钮应由一个明确的派生条件控制，例如：

```text
inputs settled
AND selected executable tasks > 0
AND no active preparation/run
AND a resolvable ffmpeg exists
```

并使用动态文案：

- `开始转码 · 12`
- `继续转码 · 5`
- `重试失败项 · 3`
- 全部成功时禁用主按钮，重复执行放入明确的重跑菜单。

## P0-4：输入导入和配置变更没有纳入运行状态，一键执行存在竞态

`useInputIngest` 会先把路径加入 `configStore.inputs`，再异步调用 `stageInputs`。在这一窗口中，旧计划仍可能处于 READY，用户可以点击开始，导致旧批次先执行，而新文件稍后才进入 staged 状态。

同时，当前配置控件在 PLANNING / RUNNING 期间仍可修改。Watcher 不会让正在运行的计划即时变化，但用户可能误以为修改已经作用于当前任务。

### 建议

- 维护 `ingestionPending`，导入完成前不允许开始；
- preparation / running 期间采取一种明确策略：
  - 简单可靠的第一版：锁定会影响本次执行的配置和队列编辑；或
  - 更成熟的队列版：允许追加，但明确标记为“下一批”，绝不混入当前 run；
- 为配置引入 revision / fingerprint。开始时冻结 revision，preparation 中 revision 变化则中止或要求重新确认；
- 禁止“UI 显示配置已改变，但实际仍执行旧参数”这种歧义状态。

## P0-5：方案声称“纯 Renderer、零架构风险”与实际需求不符

至少三项改动无法只靠 Renderer 完成：

1. **可靠的一键 prepare-and-start**：涉及主进程 `currentPlan`、规划失败回滚、选择映射和并发守卫；
2. **源/目标结构化对比**：当前 public snapshot 没有目标宽高、目标编码器、目标帧率、目标视频/音频策略等字段；
3. **系统休眠/关闭应用**：需要新的 preload API、IPC、main/native 实现、偏好持久化和终态守卫。

尤其是 `createPublicTaskSnapshot` 有意隔离内部 `dstArgs`、preset、hwPlan 等对象。若 Renderer 只根据预设名称和少量 config 字段拼“目标规格”，就无法保证目标编码器、实际分辨率和音频策略准确，尤其在硬件分层、按源文件计算和不放大策略存在时。

### 建议

不要把本方案描述为零风险前端整理。应明确拆成：

- **交互状态层**：Renderer / Pinia；
- **准备与执行编排层**：main service；
- **公共展示契约层**：`shared/contracts.ts` 与 public snapshot；
- **可选系统动作层**：native / IPC。

## 4. 重要问题与更优做法

## 4.1 不要把“一次点击”误解为“跳过 preflight”

底层 plan 阶段承担了真实的安全与正确性工作：

- 读取媒体元数据；
- 计算按源文件决定的目标参数；
- 解析硬件编码器与滤镜；
- 生成最终文件名和目录；
- 检查目标是否已存在；
- 检查源流是否满足预设；
- 构建最终 FFmpeg 参数。

更优秀的目标是“**一次用户 commit，内部自动 preflight**”，不是删除 preflight。

建议增加明确的准备阶段反馈：

```text
正在检查 37 个文件…
已解析 24 / 37，发现 2 个目标已存在，1 个缺少视频流
准备完成后显示：34 个可转码，3 个将跳过
```

如果所有任务都将跳过，应停在 preflight 汇总并解释原因，不要显示一次“完成但处理 0 个文件”的空运行。

## 4.2 当前准备阶段不可取消，长目录扫描会放大一键执行的负面感受

一键开始后，用户看到的是一个可能持续较久的“分析中”，但当前没有 preparation 取消能力。对大目录、网络盘、异常媒体或损坏文件尤其明显。

### 建议

- 第一阶段至少允许取消 preparation；
- 逐文件报告扫描 / 探测进度，而不是只有总 spinner；
- 单个坏文件应形成 task-level preflight error，不应轻易让整个目录计划全部失败；
- preparation 失败时保留上一份仍然有效的计划，而不是先销毁 `currentPlan` 再尝试构建新计划。

主进程当前会在构建开始时先清空 `currentPlan`。更稳健的做法是构造临时 plan，全部成功后再原子替换。

## 4.3 输出策略不能继续用空字符串承担多种语义

空 `outputDir` 当前确实表示“每个源文件旁边输出”，但指定输出路径后，`outputMode` 还会改变最终目录：

- `file`：直接写入指定目录；
- `dir`：写入“指定目录 + 源父目录名”；
- `tree`：按目录树重写。

因此 UI 中笼统的“输出目录”并不能准确描述最终落点。批量输入来自不同目录时，更不存在一个单一的最终目录。

### 建议模型

```text
destinationPolicy:
  - besideSource
  - customRoot

layout:
  - flat
  - preserveParentName
  - preserveTree

customRoot: last non-empty custom path
```

界面默认显示：

```text
输出：每个源文件同目录
```

选择自定义后显示：

```text
输出：D:\Export（保留各源目录名）
```

计划完成后应显示真实样例和汇总：

```text
12 个产物将写入 3 个目录
```

不要在有侧栏控件的同时再放一份可编辑底栏控件。可以保留侧栏完整配置，并在底部提供摘要和“更改”入口；两者必须使用同一个 store / shared component。

## 4.4 一键执行前需要暴露批量风险摘要

当前高风险选项 `override` 和 `deleteSource` 位于设置中。用户点击开始时，至少应能看到本批次的影响：

```text
本次将处理 37 个文件
3 个目标已存在，默认跳过
2 个目标将被覆盖
1 个文件完成后源文件将移入安全回收目录
输出：每个源文件同目录
```

这不是重新引入“生成计划”步骤，而是把高成本错误的预防信息放在 commit 之前。删除源文件仍应保留明确确认；批量覆盖是否确认可按数量和风险决定。

## 4.5 目标对比卡片会比当前界面占用更多垂直空间

当前 960×640 最小窗口下，表格、底部快速预览和 ExecutionBoard 已占据明显空间。若再加入三行源/目标卡片和独立输出条，长列表可视行数会显著下降。

建议使用两级信息：

### 默认：单行差异摘要

```text
1920×1080 H.264 → 1920×1080 HEVC NVENC · CRF 23 · AAC 192k
```

只突出发生变化的项目，并提供“展开详情”。

### 展开：结构化详情

- 源：容器、编码、分辨率、帧率、码率、音频策略；
- 目标：容器、实际编码器、分辨率、帧率、质量/码率、音频策略；
- 其他：目标路径、预计大小、跳过/覆盖原因。

如果当前选中了多个任务，不应只显示其中一个任务却让用户误以为这是批次汇总。应显示：

```text
已选 12 个 · 目标预设一致 · 源分辨率 720p–4K
```

或明确显示“正在查看第 1 个任务”。

## 4.6 目标摘要必须来自真实执行计划，而不是前端猜测

建议扩展 public contract，而不是把内部对象直接暴露给 Renderer：

```ts
interface MediaSourceSummary {
  container?: string
  videoCodec?: string
  width?: number
  height?: number
  frameRate?: number
  bitrate?: number
  audioCodec?: string
  audioChannels?: number
  audioSampleRate?: number
}

interface MediaTargetSummary {
  container: string
  videoEncoder: string
  width: number
  height: number
  frameRate?: number
  videoMode: "quality" | "bitrate"
  videoQuality?: number
  videoBitrate?: number
  audioStrategy: string
  estimatedSize?: number
  estimateAvailable: boolean
}
```

构建原则：

- 只投影 JSON-safe 展示字段；
- 目标编码器应来自实际 encoder/hw plan，而不是只显示 preset family；
- 无法可靠估算输出大小时显示“大小未知”，不要制造精确感；
- 保留现有“不得泄漏 argv、preset、临时路径、hwPlan”等边界测试。

## 4.7 播放功能要处理失败和源文件清理，不只是增加两个菜单项

`shell.openPath` 会返回错误字符串，当前调用方普遍直接 `void`，用户无法知道为什么没打开。播放操作应检查返回值并给出可恢复提示。

还需处理：

- 未成功任务禁用“播放产物”；
- 跳过但目标已存在的任务是否允许播放现有目标，需要 public plan 明确表达；
- 开启“完成后清理源文件”时，源文件可能已被移动，原路径播放会失败；
- 默认应用拒绝关联、文件被移动或权限不足时，提示“打开失败”，并保留“定位文件 / 更换默认应用”的恢复路径。

不建议本轮增加内置播放器。Electron 内置播放会引入编解码支持、音轨、字幕、全屏、seek、硬件占用和外部播放器差异等额外复杂度，收益不足以覆盖当前核心流程优化。

## 4.8 顶栏减法应消除重复，而不是把信息从一处搬到另一处

当前硬件信息在顶栏和状态栏重复出现。更好的策略是：

- 顶栏只保留应用/侧栏控制、队列摘要、主操作、运行状态；
- ffmpeg / ffprobe / 硬件能力统一收敛到状态栏或环境详情弹层；
- 正常时不常驻 CPU、内存、GPU 型号；
- 仅在 ffmpeg 缺失、硬件回退或用户选用了不兼容编码器时显示警告；
- 预设摘要可显示“HEVC · NVENC”，但不要把静态 GPU 名称当作“当前任务正在使用”的证明。

## 4.9 日志减法方向正确，但原方案的诊断部分不准确

INFO 日志不会增加当前错误徽标；真正的问题是高频参数变化污染日志内容和 500 条有限缓冲区。更合适的做法是：

- 删除 CRF 等连续控件的逐变化 INFO；
- 保留一次性的 preset / output policy 变更摘要，或放入独立 activity history；
- 保留 staging 汇总、preflight 结果、run start、task retry、FFmpeg warning/error、summary；
- ERROR 徽标只由未处理错误产生；
- 任务失败时直接提供“查看此任务错误”，无需用户自己筛日志。

## 4.10 完成后的电源动作不属于本轮核心减法

“系统休眠 / 关闭应用”有实际主进程和 OS 副作用，并且必须定义：

- 仅全部成功时执行，还是有失败也执行；
- skipped / cancelled 是否允许；
- 是否还有未选中的待处理任务；
- 用户何时确认该偏好；
- 偏好是否持久化；
- 主进程完成收尾、manifest 清理和通知后再执行；
- 关闭应用失败或被系统拦截时如何恢复。

建议本轮只保留完成通知、打开目录、播放产物、查看失败。电源动作作为独立后续功能，放入设置，而不是状态栏常驻下拉框。

## 5. 推荐的整体交互结构

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ 侧栏 | 37 个文件 · 34 个将处理         [预览详情] [开始转码 · 34]      │
├──────────────────────┬───────────────────────────────────────────────────┤
│ 配置侧栏              │ 任务列表                                          │
│ 预设 / 视频 / 音频     │ 选择、状态、源文件、目标文件、进度                 │
│                      ├───────────────────────────────────────────────────┤
│                      │ 34 个将处理 · 3 个跳过 · 输出：各源文件同目录 [更改] │
│                      │ 1920×1080 H.264 → 1080p HEVC NVENC · CRF 23  [展开] │
├──────────────────────┴───────────────────────────────────────────────────┤
│ 状态栏：ffmpeg 就绪 · 当前阶段 · 环境异常 / 日志入口                      │
└──────────────────────────────────────────────────────────────────────────┘
```

### 顶栏

- 主按钮随状态变为“开始转码 / 正在准备 / 停止 / 重试失败项”；
- 运行中用“停止”替换无用的“生成计划”和“清空”，清空移入更多菜单；
- “预览详情”是非阻断入口：需要时生成/刷新计划并打开 Inspector，不承担主流程；
- 不再同时展示“生成计划”和“开始转码”两个同等级按钮。

### 左侧配置

- 保留预设与参数调节；
- 完整输出规则可放在此处；
- 底部只显示共享的 destination summary，通过“更改”打开同一个编辑控件，不复制状态。

### 右侧任务区

- 继续使用高密度表格；
- 行焦点、执行勾选、当前 inspect 三种状态保持分离；
- 行操作以菜单为主，避免操作列过宽；
- 底部使用紧凑差异摘要，展开后再显示结构化详情。

### 状态反馈

preparation 和 execution 必须持续可见：

- 当前阶段；
- 已处理 / 总数；
- 当前文件；
- 可取消；
- 错误数量；
- 真实最终输出。

这比弱化 plan 阶段更重要。成熟工具不是没有内部等待，而是不会让等待处于无反馈状态。

## 6. 推荐的技术方案：单一“准备并开始”命令

与其在 `App.vue` 中写 `createPlanInternal()` 后再调用 `startExecution()`，更稳健的是在 main service 增加一个原子化入口，例如：

```ts
prepareAndStart({
  configSnapshot,
  selectedSourcePaths,
  configRevision
}): Promise<{
  runId: string
  preflight: {
    executable: number
    skipped: number
    invalid: number
  }
}>
```

主进程内部流程：

1. 冻结本次 config snapshot 和 revision；
2. 在临时变量中构造 plan，不先销毁上一份有效 plan；
3. 规范化源路径并映射本次选择；
4. 返回/记录 preflight 汇总；
5. 若存在可执行任务，原子切换 active plan 并启动 engine；
6. 若全部跳过或失败，不启动空 run；
7. preparation 期间支持取消和 revision 冲突检测；
8. 事件流继续通过现有 `onEngineEvent` 发送。

原有 `createPlan` 保留给“预览详情”，原有 `startExecution` 可保留为内部原语或收敛为私有方法。这样可以避免 Renderer 自己编排跨 IPC 的事务，也更容易保证主进程和 Renderer 对状态有一致认识。

如果暂时不做 main API 拆分，至少要在 Renderer 中完成以下防线：

- 抽取单一 `ensureCurrentPlan()`；
- 捕获规划前的选择路径；
- 规划后按路径恢复选择；
- 无选择直接禁用；
- 显式传 task IDs；
- 对 PLANNING、ingestion、FAILED、all-skipped 建立统一 readiness；
- 规划失败时不得继续调用 execution。

## 7. 建议实施顺序

### Phase 0：先定义状态与安全契约

- 明确 canonical queue 和稳定任务身份；
- 拆分 session phase、plan freshness、ingestion、selection；
- 规定空选择、部分完成、重规划和输入追加语义；
- 更新现有 E2E 中“STALE 时 Start 必须 disabled”的旧预期。

### Phase 1：完成安全的隐式 preflight

- 实现 prepare-and-start；
- 开始按钮动态可用和文案；
- preparation 进度、错误和取消；
- 选择按路径保留；
- 禁止空选择回退为全部执行；
- 规划失败不执行，也不破坏上一份有效计划；
- all-skipped 不启动空执行。

这是唯一应优先交付的核心体验改动。

### Phase 2：输出策略与风险摘要

- 建立显式 destination policy；
- 显示 beside-source / custom root 的真实语义；
- 显示覆盖、跳过、删除源文件数量；
- 侧栏和底栏使用同一状态源；
- 验证多来源目录与三种 output layout。

### Phase 3：完成验收闭环

- 成功任务支持播放产物；
- 源文件播放处理清理后失效；
- 捕获 `openPath` 错误；
- 右键/更多菜单提供定位和恢复动作；
- 保持主进程路径白名单不变。

### Phase 4：目标摘要契约与紧凑对比

- 增加 source/target public summary；
- 增加 snapshot 和边界测试；
- 默认显示单行差异；
- 展开显示结构化详情；
- 多选时显示批次摘要而非伪装成单项。

### Phase 5：视觉和日志降噪

- 移除高频参数 INFO；
- 合并重复硬件信息；
- 仅异常时突出环境状态；
- 在 960×640、125%/150% 缩放下检查信息密度。

### Phase 6：可选系统完成动作

- 独立设计 native capability；
- 增加偏好持久化和终态守卫；
- 不与核心一键转码捆绑发布。

## 8. 必须补充的测试与验收标准

## 8.1 自动化测试

### 一键执行状态机

- staged 文件直接点击 Start，自动 preparation 后执行；
- READY 计划点击 Start，不发生多余重规划；
- STALE 配置点击 Start，使用最新配置执行；
- planning 失败时绝不调用 execution；
- 双击 Start、按钮 + F5、菜单 + 快捷键并发时只启动一个 run；
- all-skipped 时不启动空 execution，并显示原因；
- 无选择时按钮禁用，主进程也不能把空数组解释为全部。

### 选择与队列稳定性

- 取消部分任务后调整配置，自动重规划仍保持原选择；
- 从表格移除的任务不会在重规划后复活；
- 目录展开任务与单文件任务混合时身份稳定；
- 已成功、失败、取消任务在继续执行时只按明确范围重跑；
- 完成后追加新文件只处理新批次或明确重新确认，不意外覆盖旧产物。

### 输出与破坏性操作

- beside-source 对多个源目录生成各自同目录目标；
- custom root + flat / parent-name / tree 三种布局准确；
- 目标已存在且 override=false 时显示将跳过；
- override=true 时显示覆盖数量和风险；
- deleteSource 确认取消时不规划、不执行；
- 确认后只清理成功任务，失败任务源文件保留；
- 更改输出路径后立即反映到 preflight 摘要和最终 `fileDst`。

### 元数据与播放

- target summary 与实际 FFmpeg encoder / scale / audio 参数一致；
- 硬件回退时显示实际 encoder，不显示预设名义 encoder；
- public snapshot 不泄漏 argv、preset、临时路径、hwPlan；
- 成功任务可播放，失败/不存在任务禁用；
- `openPath` 返回错误时 UI 有提示和定位恢复入口；
- deleteSource 开启后源文件播放的失效行为明确。

### 并发与输入导入

- staging 未完成时 Start 不可用；
- preparation / running 时修改配置不会影响当前 run；
- 快速连续拖入、重复拖入和目录导入不重复、不丢任务；
- preparation 可取消且不会留下 RUNNING 假状态；
- 终止发生在 manifest / engine 启动窗口时状态仍能收敛。

## 8.2 人工验收

- 首次使用者在不阅读说明的情况下，能完成“导入 → 选择预设 → 确认输出 → 开始”；
- 大目录点击 Start 后始终看得到当前阶段和取消入口；
- 960×640、1280×720、125% / 150% Windows 缩放下无关键内容截断；
- 200% 缩放时核心流程不依赖鼠标悬停；
- 全键盘可完成导入、选择、开始、停止、查看错误和播放；
- 右键菜单有 Shift+F10 / Context Menu 键盘入口；
- 焦点状态、错误状态不能只依赖颜色；
- 主题、窄窗口、200% 缩放下对比摘要和 destination summary 均可理解。

## 8.3 建议的产品指标

即使不引入遥测，也应记录内部验收基线：

- 从文件就绪到 FFmpeg 启动的耗时；
- 用户为首次成功转码执行的点击次数；
- 任务选择范围意外变化次数；
- 输出位置误判 / 找不到产物次数；
- 目标已存在、覆盖、源文件清理的误操作次数；
- preparation 失败后的恢复成功率。

本轮最核心的成功标准不是“少了一个按钮”，而是：

> **少一次技术步骤，但没有少一次安全检查。**

---

## 9. 最终结论

原方案约有一半内容可以直接吸收：隐式计划、常驻输出摘要、完成后播放、日志与静态硬件信息减法都值得做。

但实施前必须重写“优化一”和“影响面评估”，并补上三项基础能力：

1. **以源路径为稳定身份的 canonical queue / selection 语义**；
2. **单一、原子化、可取消的 prepare-and-start 流程**；
3. **真实目标摘要的 public contract**。

完成这三项后，一键转码才会从“少一步点击”真正升级为更短、更安全且可恢复的桌面工作流。否则只是把内部计划延迟藏到 Start 后面，同时引入选择扩大、任务复活、空选择执行全部和状态竞态等新风险。

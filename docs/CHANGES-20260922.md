## 20:52 新增 VP9 预设族 + 修复两个 CPU 编码/容器潜在 bug（真机实测）

## 07:58 实测方法学修订 + 编码侧能力矩阵（文档与探测工具，无 src 改动）

本文档轮次只改 **docs + 探测脚本（temp/，未入库）**，`lib/` 无改动。

### 1. 判定口径修订：新增 `UP`（软解+上传），`pixfmt:<hw>` 不能单独当硬解证据

用 `F:/temp/testvideos/mysamples`（87 个 codec×位深×色度 组合）复核后发现：
**`pixfmt:<hwfmt>` 会假阳性** —— ffmpeg 在解码器不支持该 codec 时，仍可能把**软件解码**的帧**上传**到硬件设备，
日志照样出现 `pixfmt:vulkan`（实测 ProRes / APV：NVIDIA 官方矩阵里根本没有这两个 codec 的解码器）。

修正后的判据（已写进 `temp/probe_hwdec_matrix.mjs`）：

| 判据 | 可靠性 |
| --- | --- |
| 退出码 | ❌ 硬解失败会静默软解，仍 exit=0 |
| `pixfmt:<hw>` | ⚠️ 假阳性（软解+上传） → 新增 **UP** 判定 |
| 解码器级 `Reinit context …, pix_fmt:<hw>` | ✅ 出现即真硬解，但**非必要条件**（`cuda + hevc 10bit` 真硬解却不打印） |
| CPU 时间（`-benchmark`） | ⚠️ 短切片被帧线程预读放大（ProRes 软解 3.69s vs vulkan 0.64s 的假象） |
| **厂商官方解码矩阵** | ✅ 最可靠，与实测逐条一致 |

`UP` 判定规则：有硬件像素格式 **且** 有上传证据（`Disabling host image transfers` / `hwupload` / `transfer`）→ 记 UP。
只加这一条、不要求"解码器级证据"，以免把 `cuda + hevc 10bit` 这类真硬解误降级。

**修正效果**（mysamples 交叉统计重跑）：
- `prores` vulkan 覆盖 3/3 → **0/3**；`apv` 1/1 → **0/1**；
- `cuda`≠HW 的 19 个文件中"至少一个替代通道可用" 7 → **3**（全部是 qsv：hevc 4:2:2 8/10bit、vp9 4:4:4 10bit）；
- "cuda 不行 ⇒ 其它也不行" 63% → **84%**。

### 2. 与 NVIDIA 官方矩阵交叉验证（逐条一致）

### 3. d3d12 / vulkan 管线实测（硬样本）

- **d3d12va 零解码覆盖**：硬样本上一律静默软解；显式 `-hwaccel_output_format d3d12` 后从"软解"变**硬失败**；
  `h264_d3d12va` 对 8K / 10bit 输入也打不开。
- **vulkan 的"能跑"多为假象**（软解+上传）；唯一独立价值是 **8K 4:2:0 全流程**（2.33x）。
- **qsv 是唯一能在 NVDEC 缺档（HEVC 4:2:2）跑通全流程硬件的通道**（`scale_qsv`+`h264_qsv` 6.48x）。

### 4. 编码器能力矩阵（并 ffprobe 复核产物格式）

**编码侧同样有静默降级**：`h264_qsv`/`h264_mf` 请求 `yuv422p`/`yuv420p10le` **退出码 0 但产物是 `yuv420p`**；
`hevc_nvenc` 请求 12bit 实得 10bit。

"NVENC 不支持、但别的硬件支持"的真缺口**只有两个**：

| 缺口 | 硬件替代 | 收益 |
| --- | --- | --- |
| VP9 输出（nvenc 无 VP9 编码器） | `vp9_qsv`（产物已验证） | 0.50x vs libvpx-vp9 0.24x |
| 8K H.264（nvenc 上限 4096） | `h264_mf`（真 7680x4320） | 从无硬件方案到 0.59x |

其余（10bit H.264 / 4:2:2）**所有硬件编码器都不支持真格式**（qsv/mf 只是降级），只能 libx264 ——
与代码既有注释一致。另：`h264_nvenc` 4:4:4 8bit ✅、`hevc_nvenc` 4:4:4 10bit ✅、AV1 走 `av1_nvenc`/`libsvtav1`。

## 09:40 落地元数据取值规则：bitDepth 透传（P0）+ 位深分级 / SAR 显示尺寸 / 帧率 / 封面流

按 `docs/ffmpeg/ffmpeg-metadata-fields-20260922.md` 的建议实施。**这是本轮唯一改 `lib/` 的提交。**

### 1. P0：`buildEncoderArgs()` 补 `bitDepth`（真实影响面 169 个 10bit 文件）

- 之前只收 `pixFmt`：mediainfo 路径下 `pixelFormat="YUV4:2:0"` **不含位深** → `swdec` 层不注入
  `-pix_fmt yuv420p` → 10bit 源 + h264 目标整层探测失败、白落 libx264（27.7x vs 10.9x）。
- 现在 `buildEncoderArgs(tierName, { pixFmt, bitDepth, … })`；`ffmpeg_build.buildVideoArgsFromPlan`
  传 `entry.info?.video?.bitDepth`（与 `scaleFormatOverride` 那条路一致）。

### 2. 位深分级（`lib/media_parser.js` 新增 `bitDepthOfFormat`）

`pix_fmt` 位深标记 → 已知 8bit 格式表（`KNOWN_8BIT_PIX_FMTS`）→ 显式位深（`BitDepth`/`bits_per_raw_sample`）
→ **undefined**。⚠️ 关键约定：**判不出时返回 `undefined`，不静默按 8bit**（实测 ffprobe
`bits_per_raw_sample` 缺失 68%、mediainfo `BitDepth` 缺失 3.9%/11.5%）。

### 3. 对齐判据 `needsDepthAlign()`：位深未知按"需要对齐"（保守方向）

`lib/hwaccel.js` 新增 `depthClassOf` + `needsDepthAlign`，替换原 `bitDepthOf(pixFmt) === "10bit"`。
**特意注释了为什么未知取保守方向**：对齐动作对 8bit 源无副作用（`-pix_fmt yuv420p` 本就是目标格式、
`scale_*:format=nv12` 本就是 8bit 源的硬件 sw_format，实测性能无差异），而反过来（10bit 当 8bit）
会直接 `Error while opening encoder`。同时 `scaleFormatOverride` 也改用它。

### 4. 显示尺寸：SAR 校正（真实片库 4.8% 命中）

ffprobe `sample_aspect_ratio` / mediainfo `PixelAspectRatio` → `width = codedW × SAR`（高度不变），
并保留 `codedWidth/codedHeight` 便于排查。下游三处消费点（`dstScaleNeeded`、`calcLongEdge`、
`selectTier srcW/srcH`）从此拿到**显示尺寸** —— 否则 352x288 SAR=178:163 这类会判错"是否需要缩放"。
为此在 `mediainfo.js` 的 ffprobe `-show_entries` 里补了 `sample_aspect_ratio`。

### 5. 帧率：标称优先 + 比较容差

- `media_parser.js` 新增 `normalizeFrameRate`：`r` 在 [1,240] 且与 `avg` 相对差 ≤5% → 用 `r`（标称）；
  否则用 `avg`；都无效 → undefined。依据：真实片库 37% 属 23.976 家族，`avg` 会抖到 23.974~23.980；
  而裸流的 `r` 可能是 `1200000/1`（测试集实测）→ 必须做合理性过滤。
- `ffmpeg_plan.js`：`dstFrameRate = reqFrameRate < srcFrameRate * 0.98`（**2% 容差**，附注释说明
  为何是 2%：覆盖 23.976↔24 的同族抖动，保住 23.976↔25 的真实降帧）。

### 6. 封面流排除 + DRM 兜底（真实片库 11.4% 命中）

- `fromFFprobeJson` 取视频流时排除 `disposition.attached_pic === 1`；**所有视频流都是封面时视为
  "无视频流"**（带封面的 mp3 不再被当成视频）。`mediainfo.js` 的 `-show_entries` 补了
  `stream_disposition=attached_pic`。
- 视频流缺 `codec_name`（DRM/加密，实测 `drm.m4v`）→ **抛数据错误**以触发既有的
  `getMediaInfo` provider fallback（mediainfo 能给出 `Format=AVC`），不在此处伪造字段。

### 7. 测试与验证

## 08:50 元数据字段实测分析：位深/色度/fps 的最大兼容取值（仅文档 + temp 分析脚本）

产出 `docs/ffmpeg/ffmpeg-metadata-fields-20260922.md`：对 `F:/temp/testvideos` 的
`testvideos_ffprobe.json` / `testvideos_mediainfo.json`（各 877 条、逐文件一一对应，730 个含视频流）
做交叉分析。**无 src 改动**。

核心结论：

- **位深必须以 ffprobe `pix_fmt` 为主**：`bits_per_raw_sample` **68% 缺失**（231/730 有值，为 0 的 0 个）；
  `pix_fmt` 后缀（`10le/12le/p010/p210/p410/gray10le`…）是唯一稳定来源，**无后缀=8bit** 是可靠约定。
- **mediainfo `BitDepth` 缺失 84 个**，其中 **4 个是真实 >8bit**（`gray12le`、2× cenc-VP9 10bit、`av1 444 10bit`）
  → 只用 mediainfo + 默认 8bit 会误判；另有 6 个文件两边都给不出位深。
- **两 provider 都给值时零冲突**（311/695 一致），只是覆盖不同 → 策略是「ffprobe 主 + mediainfo 兜底」，
  合并后位深可判定 95.1%、色度 96.7%（mediainfo 色度缺失 157 个中 150 个可由 pix_fmt 补）。
- **位深未知时按 10bit 保守处理是安全的**：`swdec` 的 `-pix_fmt yuv420p` 与 `cuda/qsv` 的 `scale_*:format=nv12`
  对 8bit 源都是 no-op；反过来（10bit 当 8bit）会直接编码器打不开。
- **fps 不能用 `r_frame_rate`**：72/730（10%）与 `avg_frame_rate` 差异 >0.01，极值离谱
  （`10.mpg` r=50 vs avg=25；`frame-1.h264` r=1200000/1）；另有 55 个 `avg=0/0` 需 mediainfo 兜底。
- **封面图/多视频流**：ffprobe 侧必须排除 `disposition.attached_pic=1`（实测 4 个文件，其中 1 个有 2 张封面），
  而 mediainfo 把封面标为 `@type=Image`（按 `@type=Video` 取天然正确）。
- 其余：SAR≠1 或缺失 24、旋转 18、隔行 9、HDR 36（判 HDR 用 ffprobe `color_transfer`，识别 Dolby Vision 只能用
  mediainfo `HDR_Format`）、VFR 63、`pix_fmt` 缺失 30（裸流）、色度含 `yuv410p`(4:1:0) 与 `gbrp` 两个漏网分支。

### 建议的代码改动（待批，未实施）

1. **P0：`buildEncoderArgs()` 补 `bitDepth` 透传** —— 现仅收 `pixFmt`，mediainfo 回退路径下
   `pixelFormat="YUV4:2:0"` 不含位深 → `swdec` 层不注入 `-pix_fmt yuv420p` → 10bit 源 + h264 目标仍打不开编码器
   （`scaleFormatOverride` 那条路已传 bitDepth，两条路需一致）。
2. 位深取值按分级实现并把 `unknown` 显式传下去（不静默按 8bit）。

4. 主视频流选择排除 `attached_pic`；`--dimension` 用 SAR/旋转校正后的显示宽高。
5. ffprobe `codec_name` 缺失（DRM）时用 mediainfo `Format` 兜底。

## 07:58 实测方法学修订 + 编码侧能力矩阵（文档与探测工具，无 src 改动）

本文档轮次只改 **docs + 探测脚本（temp/，未入库）**，`lib/` 无改动。

### 1. 判定口径修订：新增 `UP`（软解+上传），`pixfmt:<hw>` 不能单独当硬解证据

用 `F:/temp/testvideos/mysamples`（87 个 codec×位深×色度 组合）复核后发现：
**`pixfmt:<hwfmt>` 会假阳性** —— ffmpeg 在解码器不支持该 codec 时，仍可能把**软件解码**的帧**上传**到硬件设备，
日志照样出现 `pixfmt:vulkan`（实测 ProRes / APV：NVIDIA 官方矩阵里根本没有这两个 codec 的解码器）。

修正后的判据（已写进 `temp/probe_hwdec_matrix.mjs`）：

| 判据 | 可靠性 |
| --- | --- |
| 退出码 | ❌ 硬解失败会静默软解，仍 exit=0 |
| `pixfmt:<hw>` | ⚠️ 假阳性（软解+上传） → 新增 **UP** 判定 |
| 解码器级 `Reinit context …, pix_fmt:<hw>` | ✅ 出现即真硬解，但**非必要条件**（`cuda + hevc 10bit` 真硬解却不打印） |
| CPU 时间（`-benchmark`） | ⚠️ 短切片被帧线程预读放大（ProRes 软解 3.69s vs vulkan 0.64s 的假象） |
| **厂商官方解码矩阵** | ✅ 最可靠，与实测逐条一致 |

`UP` 判定规则：有硬件像素格式 **且** 有上传证据（`Disabling host image transfers` / `hwupload` / `transfer`）→ 记 UP。
只加这一条、不要求"解码器级证据"，以免把 `cuda + hevc 10bit` 这类真硬解误降级。

**修正效果**（mysamples 交叉统计重跑）：
- `prores` vulkan 覆盖 3/3 → **0/3**；`apv` 1/1 → **0/1**；
- `cuda`≠HW 的 19 个文件中"至少一个替代通道可用" 7 → **3**（全部是 qsv：hevc 4:2:2 8/10bit、vp9 4:4:4 10bit）；
- "cuda 不行 ⇒ 其它也不行" 63% → **84%**。

### 2. 与 NVIDIA 官方矩阵交叉验证（逐条一致）

Ada 5th-gen NVDEC：HEVC 4:4:4 = YES、HEVC 4:2:2 = NO、H.264 4:2:2 = NO、H.264 10bit = NO、VP9 仅 4:2:0；
VVC/AVS2/AVS3/ProRes/APV/Theora/MSMPEG4 无解码器。本机 5 通道实测与之一致。

### 3. d3d12 / vulkan 管线实测（硬样本）

- **d3d12va 零解码覆盖**：硬样本上一律静默软解；显式 `-hwaccel_output_format d3d12` 后从"软解"变**硬失败**；
  `h264_d3d12va` 对 8K / 10bit 输入也打不开。
- **vulkan 的"能跑"多为假象**（软解+上传）；唯一独立价值是 **8K 4:2:0 全流程**（2.33x）。
- **qsv 是唯一能在 NVDEC 缺档（HEVC 4:2:2）跑通全流程硬件的通道**（`scale_qsv`+`h264_qsv` 6.48x）。

### 4. 编码器能力矩阵（并 ffprobe 复核产物格式）

**编码侧同样有静默降级**：`h264_qsv`/`h264_mf` 请求 `yuv422p`/`yuv420p10le` **退出码 0 但产物是 `yuv420p`**；
`hevc_nvenc` 请求 12bit 实得 10bit。

"NVENC 不支持、但别的硬件支持"的真缺口**只有两个**：

| 缺口 | 硬件替代 | 收益 |
| --- | --- | --- |
| VP9 输出（nvenc 无 VP9 编码器） | `vp9_qsv`（产物已验证） | 0.50x vs libvpx-vp9 0.24x |
| 8K H.264（nvenc 上限 4096） | `h264_mf`（真 7680x4320） | 从无硬件方案到 0.59x |

其余（10bit H.264 / 4:2:2）**所有硬件编码器都不支持真格式**（qsv/mf 只是降级），只能 libx264 ——
与代码既有注释一致。另：`h264_nvenc` 4:4:4 8bit ✅、`hevc_nvenc` 4:4:4 10bit ✅、AV1 走 `av1_nvenc`/`libsvtav1`。

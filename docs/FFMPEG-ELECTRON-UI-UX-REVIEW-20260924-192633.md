**值得肯定的（应保留）**

## 2. 本轮改动（v1.2.0 → v1.3.0）逐项评估

本轮共 5 项新增，其中 **1 项是真正的减法，4 项是加法**。逐项判定：

| # | 改动 | 判定 | 理由 |
| :--- | :--- | :--- | :--- |
| 1 | 全域拖放感知 + Hero 空态大画板 | **过度** | 全域蒙层与已有左栏 dropzone **职责重复**；Hero 画板只服务"零输入"这一瞬时状态，却占掉整个主视区。主流做法（HandBrake/Media Encoder）空态只给一句提示 + 一个按钮，不做整屏引导画板 |
| 2 | 微调参数脏标记（Dirty State）+ 一键还原 | **可接受但过度实现** | "哪些参数被改过"确有价值，但实现代价是 **11 个圆点 + 9 个单项撤销按钮 + 2 个"还原 N 项"链接 + 计数逻辑**，信息密度远超收益。主流做法是"改动项加粗/换色"或"重置全部"一个按钮 |
| 3 | TaskInspectorDrawer 取代常驻命令折叠条 | **优秀，本次唯一高质量减法** | 释放主视区垂直空间、按需呼出、符合渐进式披露；且把"元数据对比 + 命令 + 单任务日志"聚到一处，语义内聚。**但落地数据链路有硬缺口（见 §3.2）** |
| 4 | STALE 过期平滑容错 | **方向优秀，落地冗余** | 不销毁任务列表是对的（优于架构原方案的硬冻结）。但呈现用了四重提示（见 §3.6），且 STALE 未进契约状态机（见 §3.1） |
| 5 | 失败任务直达关联日志 | **正确的小改进** | 失败→日志是真实高频排障路径，成本低。**但原型实现与真实事件契约不匹配（见 §3.7）** |

**结论**：本轮 5 项中 4 项为加法，只有第 3 项是减法。**"每一次改动都在做加法"的判断成立**——而且加法的成本正在从"文档变长"转为"主面板变挤"。

### 3.1【P0】设计文档与架构文档 4 处正面冲突，两份都标"定稿"

两份文档互为交叉引用（设计文档 §1 声明"只定义 UI/UX，技术以架构文档为准"），但在下面 4 点结论相反，实现者按任一份做都会与另一份矛盾：

| 冲突点 | 设计文档 v1.3.0 | 架构文档 v1.2.0 | 事实裁定 |
| :--- | :--- | :--- | :--- |
| **STALE 状态** | §5 状态机表格新增 STALE 行；§4.1 顶栏胶囊宣称"六态文案" | §6.1 状态机**无 STALE**；§0.2 明确"**纯 renderer**，主进程校验不做" | 裁定：STALE 只能是 **renderer 本地派生状态**，不能写入 `RunnerState` 契约。设计文档应改写为"UI 派生状态，非引擎状态"，避免实现者去改 `contracts.ts` |
| **`jobs` 并发** | §4.5 暴露 `NInputNumber`（1–4），§1.2 列入"核心功能齐全" | §0.2 决策表："**v1 固定 concurrency=1，无 jobs UI**" | 裁定：**架构文档为准，v1 砍掉 jobs**。设计文档 §4.5 应删该行，§1.2"覆盖并发"应删 |
| **`deleteSourceFiles` 删除源** | §4.5 暴露高危开关 + §6.4 确认弹窗 + §9 P3 验收项 | §0.2 决策表："**v1 不在 UI 暴露**，CLI 保留" | 裁定：**架构文档为准，v1 砍掉**。但设计文档 §6.4 文案本身准确（与 `safeRemove` 实测行为一致），**建议保留文案供 v2 复用，UI 不暴露** |
| **FPS 指标** | §4.6 执行看板"下行：单项百分比进度与实时 FPS" | §0.2："**砍掉**，只留倍速/进度/ETA"；§7.5"不显示 FPS（无数据依据）" | 裁定：**架构文档为准**。实测 `ffmpeg_run.js` 的 `onProgress` 只回 `{percent, speed, currentTime, srcDuration}`，**确无 frame 数据**，FPS 必须伪造。设计文档应删 |

### 3.2【P0】TaskInspector 的"完整 FFmpeg 命令"拿不到数据

设计文档 §4.6 承诺检查器展示"**FFmpeg 完整命令**：等宽字体着色展示，支持一键复制"。但实测数据链路：

- `PublicPlanSnapshot` 结构（`apps/mediac-desktop/src/shared/contracts.ts`）中，命令只有**计划级单一字段** `previewCmd: string`；
- `lib/ffmpeg_plan_snapshot.js` 的 `createPublicPlanSnapshot` 明确只投影 `previewCmd`，**任务对象（`tasks[]`）没有任何命令字段**；
- 原型 §`buildCmd(t)` 是**前端凭 `preset + tune` 现场拼字符串**（`ffmpeg -i "..." … -c:v libx265 …`），**不是真实推演结果**。

**后果**：真机实现时，检查器要么只能显示计划级 `previewCmd`（无法"按行双击看该任务命令"），要么必须在渲染进程复刻一遍 ffmpeg 参数拼装逻辑——而后者**直接违反设计文档 §1 硬约束"所有转码逻辑在 lib 层，渲染进程只消费快照与事件"**。

**修法（二选一）**：
- **A（推荐）**：`PublicPlanSnapshot.tasks[]` 增补 `previewCmd?: string`（每任务一行命令），由 `lib/ffmpeg_plan_snapshot.js` 投影。注意脱敏：现有快照已刻意剥离 `preset 实例/argv/临时路径`，**增补时必须确认命令里不含 `fileDstTemp` 临时路径**，否则会泄漏内部实现细节。
- **B（降级）**：检查器只展示计划级 `previewCmd` + 该任务的参数差异摘要（源规格 vs 目标规格），文案改为"计划命令预览"，**不承诺"该任务完整命令"**。

**无论选哪个，设计文档 §4.6 与 §7.3 必须同步改**——现在这两处互相印证了一个不存在的能力。

### 3.3【P0】预设徽章 `maxBitrate` 不在 IPC 契约里

设计文档 §4.3 要求预设选项"**两行**：主行 preset 名 + 次行关键指标摘要（`HEVC · 1080p · CRF 23 · 峰值 8M · aac 192k`）"，§7.4 又把 `maxBitrate` 列为徽章字段。

**实测结论**（脚本 `temp/uiux-check-presets.mjs`）：

- `presets/default.yaml` 中 **29 个公开预设，其中 21 个原始预设持有 `maxBitrate`**（如 `hevc_2k.maxBitrate = 8000000`）；
- 但 `apps/mediac-desktop/src/main/ffmpeg-service.ts` 的 `getSummary()` 映射 `EnvironmentSummary.presets` 时，**只映射了 9 个字段**：`name / type / format / videoCodecFamily / audioCodec / videoQuality / videoBitrate / audioBitrate / dimension`；
- **`maxBitrate` 不在其中**，且 `contracts.ts` 的 `EnvironmentSummary.presets` 类型定义里也没有它。

**后果**："峰值 8M"这个主力徽章在真机**永远拿不到值**，会静默降级为空（设计文档 §7.4 写了"字段缺失时隐藏对应徽章"，等于该徽章直接消失）。而"峰值码率"恰恰是这批预设最有信息量的差异化指标（`8M/12M/5M` 区分 `2k/2kh/2kl`）。

**修法**：`contracts.ts` 的 `EnvironmentSummary.presets` 增补 `maxBitrate: number`；`ffmpeg-service.ts` 的映射加一行 `maxBitrate: preset?.maxBitrate || 0`。**这是三行代码的改动，但不做则该设计点整体失效。**

**另需注意**：实测 `videoCodecFamily` 对 **6 个音频预设全部为空字符串**（`audio_extract / aac_high / aac_medium / aac_low / aac_he / aac_voice`）。设计文档 §4.3 的分组规则是"按 `type` + `videoCodecFamily` 分五组"，实现时**必须先按 `type === "audio"` 分流，再按 family 分组**，否则这 6 个预设会掉进空分组。文档应显式写出这个分流顺序。

### 3.4【P0】`hwaccel` 取值域与真实语义不符，UI 交互模型错误

设计文档 §4.5 给出 `hwaccel`：`auto / cuda / qsv / amf / d3d / cpu`，`decodeMode`：`auto / gpu / cpu`，两者做成**两个并列的独立下拉**。原型 §`HW_OPTS` 完全照抄。**实测（`temp/uiux-check-hwaccel.mjs`）证明这个模型有三个错**：

**错误 1：`cpu` 不会纯软解。**
实测 `candidateTiers(caps, {decodeMode:"auto", hwaccel:"cpu"})` → `["cuda","cpu"]`。源码注释写明"`--hwaccel auto` 视为未显式指定"，但**实测 `cpu` 同样落入"未显式指定"分支**（`normalizeHwaccelName("cpu")` 返回 `"cpu"`，代码显式跳过 `name !== "cpu"` 的白名单过滤）。**UI 上让用户选"cpu · 纯软件"，实际仍会走 CUDA 硬件解码——这是会误导用户的错误承诺。**

**错误 2：`decodeMode=gpu` + `hwaccel=auto` 直接抛异常。**
实测：`candidateTiers(caps, {decodeMode:"gpu", hwaccel:"auto"})` → **`THROW: hwaccel 'd3d' is not available on this machine`**。原因是 `auto` 经 `normalizeHwaccelName` 归一化成了 `d3d`，而 NVIDIA 机器上 `d3d` 不可用。**但 UI 把两个下拉做成自由组合**，用户完全可以选出 `decodeMode=gpu + hwaccel=auto` 这个**必然报错**的组合，且界面上没有任何约束或提示。

**错误 3：`d3d` 是层名，不是 ffmpeg 的 `-hwaccel` 值。**
实测真实 `-hwaccel` 值域含 `d3d11va`、`d3d12va`、`dxva2`、`vulkan`（源码 `HwAccel` 常量），而 `d3d` 是内部**层名**。UI 暴露 `d3d · 通用兜底` 这个选项，语义上对用户没有可操作性。

**修法（推荐：把两个下拉合并成一个"解码策略"三选一）**：

| UI 选项（文案） | 映射 | 说明 |
| :--- | :--- | :--- |
| 自动（推荐） | `decodeMode=auto, hwaccel=auto` | 逐层探测降级，最稳 |
| 仅软件解码（CPU） | `decodeMode=cpu` | **实测唯一能保证纯软解的路径**，文案必须对应 `decodeMode` 而非 `hwaccel` |
| 指定硬件解码器 | `decodeMode=gpu` + 显式 `hwaccel` | 需从 `getEnvironment().hardware.usable` **动态渲染**可用项，**禁用/隐藏不可用项**（如 NVIDIA 机器上不显示 qsv/amf） |

这样既消除"必然报错组合"，也让"纯软解"这个承诺真实成立。**若坚持保留两个下拉，则必须：`decodeMode=gpu` 时把 `hwaccel` 的 `auto` 选项禁用并强制选择具体值；且 `hwaccel=cpu` 的文案改为"不指定加速器"而非"纯软件"。**

### 3.5【P1】主面板持续做加法：把"能力齐全"当成了"主面板齐全"

这是用户"越改越复杂"直觉的核心。量化对比设计文档 v1.2 → v1.3 与架构文档的走向：

| 维度 | 现状 | 同期架构文档决策 |
| :--- | :--- | :--- |
| 左栏卡片 | **5 张**（输入输出 / 预设 / 视频 / 音频 / 高级） | 在砍 jobs、删源 |
| 左栏控件 | **11 个可编辑控件** + 输入 chips + 命名 2 项 | — |
| 脏状态元素 | **11 个圆点 + 9 个单项撤销 + 2 个"还原 N 项"** | — |
| 抽屉 | **2 个**（检查器 460px + 日志 480px） | — |
| 全屏蒙层 | **1 个**（拖放） | — |
| 表格列 | **9 列** | 架构文档 §7.4 只列 7 列（无"大小""解码→编码"） |
| 顶栏元素 | 品牌 + **4 个徽章** + 3 个图标按钮 | — |

**关键矛盾**：架构文档明确"**v1 做减法**——砍掉删除源、并发控制、自动重试、FPS、单实例锁……把核心链路做扎实"，而**同一周的 UI 设计稿却反向做了 4 项加法**（全域拖放、脏状态、检查器、日志聚焦）。两份文档的复杂度曲线**方向相反**。

**这不是说 UI 不该细化**，而是：**架构在砍"引擎能力"，UI 在加"呈现层元素"**，而呈现层元素本身也要占用开发工时与用户的认知带宽。当左栏有 11 个控件、表格有 9 列、还有 2 个抽屉时，用户第一次打开应用的感受不是"功能强大"，而是"不知道从哪下手"。

**修法**：见 §6 的主面板分层方案。

### 3.6【P1】STALE 提示四重冗余，960px 下工具栏一行四段拥挤

设计文档 §5 让 STALE 同时出现在 4 个位置：

1. 顶栏状态胶囊变色（"参数已修改"）
2. 工具栏"生成计划"按钮**变 primary + 脉冲高亮**，文案改"更新计划"
3. 工具栏新增**独立警告 pill**"参数已变更，请点击「更新计划」"
4. 表格整体**半透明**（`.is-stale tbody{opacity:.75}`）

**截图实测（`mediac-desktop-ui_stale.jpg`）证实**：工具栏一行内变为"更新计划 + 开始转码 + 终止 + 清空任务 + 警告 pill + 任务统计"，**五段内容挤在一行**，且"清空任务"与警告 pill 间距目测仅约 10px，整行节奏很紧。窗口最小宽度是 **960px**（`main/index.ts` 的 `minWidth`），此时必然换行或压缩。

同时存在**语义重复**：胶囊已说"参数已修改"，pill 又说"参数已变更，请点击更新计划"，按钮本身还变成了"更新计划"并高亮。**三处说同一件事，属于典型的"信息过载式强调"**。

**修法（保留 2 处即可）**：
- **保留**：工具栏按钮变 primary + 文案改"更新计划"（**这是行动入口，最强引导**）；
- **保留**：表格轻微降透明度（表示"当前表格不是最新计划"，是状态而非文字）；
- **删除**：工具栏独立警告 pill（与按钮文案完全重复）；
- **删除或弱化**：顶栏胶囊的 STALE 态（顶栏胶囊应表达**引擎运行态**，而 STALE 是"配置相对计划过期"的派生状态，语义不同层；混在同一个胶囊里会让用户以为引擎出了问题）。

### 3.7【P1】任务表 9 列在最小窗宽必然截断，"解码→编码"属详情信息

设计文档 §4.6 定义 **9 列**：多选 / # / 源文件 / 大小 / 时长 / **解码 → 编码** / 目标文件 / 状态 / 操作。而架构文档 §7.4 只定义 **7 列**（无"大小""解码→编码"）。

**截图实测证实截断**（多张截图一致）：
- 源文件列子行："`H.264 · 3840×2160 · 29.97fps · D…`"、"`…60fps · C:\U…`"——**路径与 fps 被切**；
- 解码→编码列子行："`解码 auto · libx2…`"——**`libx265` 被切**；
- 目标文件列："`[SHANA] 工作录屏_20260921_hevc_…`"——**被切**。

**根本问题**：960px 宽时，左栏（380px 可收起）+ 表格 9 列，**每列平均不足 65px**。而"解码 → 编码"这一列的**主信息量（`H.264 → HEVC`）与状态列的"转码中"是同一类信息的不同粒度**——用户在主面板真正需要的是"这条任务要变成什么"，而不是"解码器是 auto 还是 libx265"。

**修法**：
- **主表收到 7 列**：多选 / # / 源文件（文件名 + 尺寸/时长合并进子行）/ 目标文件 / **编码转换**（只留 `H.264 → HEVC` 主文字，删掉"解码 auto · libx265"子行）/ 状态 / 操作；
- **被删的"解码模式 + 实际编码器"下沉到 TaskInspector**——**这正是检查器存在的意义**；
- 同时**列宽改用 `min-width` 而非固定 `%` + 固定 px 混合**（现状 `25%/84px/80px/130px/25%/120px/108px` 混用，最小窗宽下弹性不足），并让"源文件/目标文件"两列可弹性伸缩、其余列固定。

**收益**：主表信息密度下降、截断消失、与架构文档 §7.4 一致，且给检查器找到了明确的职责。

### 3.8【P1】双抽屉层级与遮挡问题

设计文档 §2.2 定义两个右侧抽屉：**检查器 460px + 日志 480px**。截图实测（`mediac-desktop-ui_inspector.jpg`）暴露：

1. **抽屉遮住顶栏全局状态区**：顶栏右侧的徽章与图标按钮被抽屉压住，只露出"演示数"两个字被硬切一半；
2. **抽屉遮住工具栏右侧任务统计**（"7 个任务 · 4.9 GB · 2:24:36" 完全不可见）；
3. **抽屉遮住表格的状态列与操作列**（这是主面板最需要交互的两列）；
4. **两个抽屉层级关系未定义**：日志抽屉 `z-index:90`、检查器 `z-index:95`。如果用户从检查器里点"查看报错"跳日志，**两个抽屉会叠加**，界面变成两层遮罩，用户不知道自己在哪一层；
5. **无焦点陷阱**：原型只在弹窗里做了 `focus()`，两个抽屉都没有 focus trap、没有 `aria-hidden` 管理、打开抽屉后 `Tab` 仍可跳到被遮挡的主面板控件（`role="dialog" aria-modal="true"` 已声明，但行为未配套）。

**修法**：
- **抽屉改为"压住主区、不压顶栏"**：`top: 52px`（顶栏高度）而非 `inset: 0`，保住全局状态胶囊与日志/设置入口的可见性；
- **明确"同时只开一个抽屉"**：从检查器跳日志时**先关检查器再开日志**（或让日志作为检查器内部的一个 tab），避免叠加；
- **补焦点陷阱**：打开抽屉时 `Tab` 循环限制在抽屉内，`Esc` 关闭后焦点归还触发元素；`aria-hidden` 同步主区。

### 3.9【P2】原型的真实缺陷（会导致演示时出丑）

以下为读原型代码发现的**功能性 bug**，不影响设计结论但影响演示可信度：

**bug 1：一次拖放会添加两次文件。**
`document` 级 `drop` 监听（全局蒙层用）与 `dropzone` 级 `drop` 监听**同时存在**，且 `dropzone` 的监听**没有 `stopPropagation`**。文件拖到左栏 dropzone 上释放时，**dropzone 的 handler 先触发一次 `addMockFile()`，事件继续冒泡到 `document` 的 handler 再触发一次 `addMockFile()`**——演示时会出现"拖一个文件进去，列表多了两个"。修法：`dropzone` 的 drop handler 加 `e.stopPropagation()`，或统一由 document 级 handler 处理。

**bug 2：`init()` 里重复初始化输入。**
`S.inputs = seedInputs(); renderInputs();` 在 `init()` 中**出现了两次**（一次在前段，一次在 `bindAll()` 之后），且 `buildPlan()` 也被提前调用。后果是初始化时输入清单被渲染两遍、计划被构建两次。属于重构残留。

**bug 3：命令预览死代码残留。**
原型已删除"命令预览折叠条"的 DOM，但 CSS 里 `.cmd-preview`、`.cmd-head`、`.cmd-body`、`.cmd-preview.open` 等**样式规则仍保留**（约 9 处），`updateCmdPreview()` 函数也仍在（改为只更新检查器内的 `inspCmdBox`）。建议清理，避免实现者误以为该组件仍存在。

**bug 4：日志聚焦过滤条件与真实事件契约不匹配。**
原型用 `l.text.indexOf("[" + focusedTaskId + "]")` 做聚焦过滤，依赖日志文本里手工拼的 `[taskId]` 前缀。但**真实契约是结构化字段**：`ENGINE_EVENT.TASK_LOG` 的 payload 是 `{taskId, taskIndex, attempt, message}`，`taskId` 是**独立字段而非文本前缀**。真机实现必须按字段过滤。设计文档 §4.7 应写明"按 `taskId` 字段过滤"，而非留给实现者从原型猜。

**bug 5：`bindAll()` 里对 `btnClearLogFocus` 的重复绑定。**
该元素在 `viewTaskLog()` 里被 `innerHTML` 重建后又立即 `addEventListener`，而初始 DOM 中已存在同名 id 的元素。多次聚焦不同任务会累积监听器。属于实现细节，但真机用 Vue 时应改为声明式绑定。

| **空态** | 一句提示 + 主操作按钮 | **整屏 Hero 引导画板 + 4 个能力 chips** | ⚠️ 过度（见 §4.2） |

| **无障碍** | 焦点管理、`aria`、键盘可达 | 有 `role`/`aria-label`/`:focus-visible`；**抽屉缺焦点陷阱** | ⚠️ 部分缺失 |

### 4.1 全域拖放的过度之处

全域拖放本身是现代做法（VS Code、Figma 都支持），但本方案有两个具体问题：

1. **与左栏 dropzone 职责重复**：左栏已有虚线投放区（`#dropzone`），现在又加了全窗口蒙层。用户拖文件到左栏投放区时，**蒙层会盖住整个界面**（`z-index:200`），反而看不见自己正在投放的投放区。**全域蒙层应该只在"拖到主区/表格区"时出现**，或者干脆去掉蒙层、只保留投放区高亮。
2. **全屏蒙层遮挡上下文**：`.global-drop-mask` 用 `rgba(16,16,20,.82)` + `blur(4px)` 覆盖全屏。用户拖文件时**看不见任务表当前内容**，无法判断"我这次拖进去会不会和已有任务重复"。**主流做法是保持界面可见，只高亮投放目标。**

**建议**：去掉全屏蒙层；保留左栏投放区（已有）+ 给主区表格加"拖入此处添加"的**轻量高亮边框**（不遮挡内容）。这样既支持全域拖放，又不丢上下文。

### 4.2 Hero 空态画板的过度之处

Hero Dropzone 在 Web 产品（Linear、Notion 空态）中常见，但**桌面批处理工具的空态是一次性瞬时状态**——用户打开应用后 5 秒内就会添加文件，之后**永远不再看到这个画板**。而它占掉了整个主视区（`.hero-empty{position:absolute;inset:0}`）。

主流做法对比：HandBrake 空态只显示一句"拖入文件或点击 Source 打开"；Media Encoder 空态显示"将文件拖入队列"；Shutter Encoder 空态是简洁的输入区。**没有一家做整屏引导画板 + 4 个能力标签。**

**建议**：简化为**居中一行提示 + 一个主按钮**（"拖入媒体文件或目录，或 [选择文件]"），删掉 4 个能力 chips（`MP4 / MKV / MOV`、`HEVC / H.264 / AV1`、`音频提取 / 压制`、`NVENC 硬件加速`——这些是营销信息，不是操作引导）。

### 4.3 参数不弹窗的决策是正确的

设计文档 §2.3 明确"常规参数**不用弹窗**（面板内折叠可见，便于批量对照）；仅系统级设置进 SettingsModal"，并给出了 HandBrake / Shutter Encoder / FFmpeg Batch AV 的对照论证。**这个决策完全正确，与主流一致**——批量转码需要持续对照参数，弹窗会打断工作流。

**但需注意**：这个原则与用户"次要设置做弹框"的直觉**方向相反**。区别在于"次要设置"指的是**系统级配置**（工具路径、GPU、主题），而不是"不常用的转码参数"。详见 §6。

## 5. 方案合理性总体评价

### 5.1 优秀之处（应作为基线保留）

1. **技术选型正确**：Naive UI（`NDataTable` 虚拟滚动开箱即用、暗色主题、`size="small"`）+ Pinia + VueUse，完全匹配高密度桌面工具需求，**避免了手写表格/弹窗的重复造轮子**。
2. **"计划先行"的产品逻辑**：默认 dry-run 预览再执行，与 CLI 语义一致，是批处理工具的正确姿势（用户可在执行前发现"选错预设/输出目录"这类昂贵错误）。
3. **硬约束写得清楚**：预设动态渲染（禁止写死）、参数走 `OPTION_KEYS` 白名单、转码逻辑在 lib 层——这三条是防止 UI 层腐化的关键约束。
4. **桌面集成完整**：任务栏进度、系统通知、`showInFolder`、防休眠，覆盖了"长任务桌面应用"的必备集成。
5. **文案与真实行为对齐**：删除源回收目录文案经实测与 `safeRemove` 行为一致，没有沿用错误的"系统回收站"说法。
6. **TaskInspector 的语义内聚**：把"源/目标规格对比 + 命令 + 单任务日志"三件排障信息聚在一处，比原先"底部命令条 + 全局日志"的割裂设计好得多。

### 5.2 需要修正的方向

| 方向 | 具体 |
| :--- | :--- |
| **先解决文档冲突** | §3.1 的 4 处冲突必须在编码前裁定，否则实现者无所适从 |
| **补齐数据链路** | §3.2（per-task 命令）、§3.3（`maxBitrate`）是"设计得很好但拿不到数据"的典型，**不做则对应设计点整体失效** |
| **修正硬件加速交互模型** | §3.4 的"必然报错组合"和"纯软解假承诺"必须在 UI 上消除 |
| **主面板做减法** | §6 的分层方案 |
| **收敛提示冗余** | §3.6 的 STALE 四重提示收敛到 2 处 |
| **表格列收敛** | §3.7 的 9 列收到 7 列，详情下沉检查器 |
| **修原型 bug** | §3.9 的 5 个问题（尤其拖放双触发，演示会出丑） |

### 5.3 关于"是否合理和优秀"的总体判断

**方案的整体架构与选型是合理且接近优秀的**，尤其在"桌面范式落地"和"技术选型"上明显高于一般水平。它的问题不在方向，而在**三个失衡**：

1. **文档间失衡**：架构在砍能力、UI 在加元素，且互相矛盾未裁定；
2. **设计与数据失衡**：多处设计点（per-task 命令、`maxBitrate`、FPS）依赖尚不存在的数据；
3. **主面板与详情失衡**：把本该"按需查看"的信息（解码器细节、完整命令、能力清单）放进了常驻视野。

**这三者都可修，且修改量不大**（主要是删减与三处契约补字段）。修完之后，这个方案可以称为优秀。

## 6. 主面板应该放什么（核心结论）

这是用户最关心的问题。先给判断标准，再给分层结论。

### 6.1 判断标准：什么才配进主面板

对批处理转码工具，**主面板（左配置栏 + 右任务表 + 底执行条）只应承载"每次转码都要动、且不动就会出错"的东西**。三条判定线：

1. **频次**：是否**几乎每次**都要设置？（偶尔改一次的不算）
2. **后果**：不设置是否会**直接导致错误结果**？（如选错预设 → 输出体积/画质全错）
3. **对照**：是否需要在**批量任务执行期间持续可见**？（如进度、失败计数）

三条命中任意两条 → 主面板；只命中一条 → 折叠区；一条都不命中 → 设置弹窗或抽屉。

### 6.2 按此标准分层

#### 第一层：主面板常驻（真正核心，7 项）

| 项 | 为什么必须常驻 |
| :--- | :--- |
| **① 输入清单**（添加文件/目录 + 列表 + 去重） | 每次都要动；不添加就没任务 |
| **② 输出目录 + 输出模式** | 每次可能变；选错 → 产物写错地方（昂贵错误） |
| **③ 预设选择**（含关键指标摘要） | **最高频且后果最重**：决定编码族/分辨率/质量，选错全盘皆错 |
| **④ 生成计划 → 开始转码 → 终止** | 主流程入口，必须一眼可见 |
| **⑤ 任务表**（源文件 / 目标文件 / 状态 / 操作） | 批量执行期间的唯一对照视图 |
| **⑥ 执行进度**（总进度 + 当前文件 + 速度/ETA） | 长任务期间必须持续可见 |
| **⑦ 失败/跳过结果与重试** | 批量执行后必须立即处置 |

**这 7 项构成了"打开就能完成一次转码"的完整闭环。** 注意：①②③ 在左栏，④⑤⑥⑦ 在右栏——**现有左右分栏结构是对的，不需要改布局**。

#### 第二层：左栏折叠区（保持折叠，不做弹窗）

| 项 | 为什么折叠而非弹窗 |
| :--- | :--- |
| **视频微调**（尺寸 / 质量 / 码率 / 帧率 / 倍速） | 中频：进阶用户会调，但多数人用预设默认。**必须折叠可见**——因为用户需要"知道可以调"，且调整后要能立刻看到摘要变化与预设的差异 |
| **音频微调**（编码 / 码率） | 低频，同上 |
| **输出命名**（前缀 / 后缀） | 低频；但改错会导致文件名混乱，需可见 |
| **高级：覆盖已存在产物 / 严格模式** | 低频但影响行为语义，需可见 |

**关键判断：这些不该做弹窗。** 理由（也是主流做法）：批量转码时用户会**反复微调 + 反复生成计划对照**，弹窗会打断这个循环；而且折叠卡片已经把"不占视野"和"随时可调"兼顾了。设计文档 §2.3 的论证是对的。

#### 第三层：独立弹窗（系统级配置，进 SettingsModal）

| 项 | 为什么弹窗 |
| :--- | :--- |
| **主题**（暗/亮） | 一次性设置 |
| **工具路径**（ffmpeg / ffprobe / mediainfo） | 装完就不动 |
| **硬件信息**（GPU 列表、编码器数、hwaccel 列表） | 只读展示 |
| **关于/版本** | 一次性 |

**现状已经做对了**——设计文档 §4.8 的 SettingsModal 内容正是这些。**这一层不需要改。**

#### 第四层：按需抽屉（详情与排障，不占主面板）

| 项 | 为什么抽屉 |
| :--- | :--- |
| **完整 FFmpeg 命令** | 排障时才看，且很长 |
| **源/目标规格详细对比** | 排障时才看 |
| **单任务日志** | 排障时才看 |
| **全局运行日志** | 低频，且很长 |

**现状的 TaskInspectorDrawer + LogPanel 已经做对了**，这是本轮最好的改动。

### 6.3 应该被砍掉或移出主面板的（关键减项）

以下 5 项**按 §6.1 标准都不该留在主面板**：

| 项 | 现状 | 建议 | 理由 |
| :--- | :--- | :--- | :--- |
| **`jobs` 并发数** | 左栏高级卡（1–4） | **删除** | 架构文档已决定 v1 固定 `concurrency=1`；且实测视频本就串行，只有音频并行——**为极低频场景保留一个控件不值得** |
| **`deleteSourceFiles` 删除源** | 左栏高级卡（高危红字） | **删除** | 架构文档已决定 v1 不暴露；这是**唯一能造成数据损失的开关**，砍掉即消除整类风险 |
| **FPS 实时指标** | 执行看板 | **删除** | 实测 `onProgress` 无 frame 数据；伪造数字比不显示更糟 |
| **"解码 → 编码"子行** | 任务表常驻 | **下沉检查器** | 主表只需 `H.264 → HEVC`；`解码 auto · libx265` 是排障信息 |
| **全域拖放全屏蒙层** | 全屏覆盖 | **删除蒙层**，保留投放区高亮 | 拖放时不该丢失任务表上下文 |

**砍掉这 5 项后的收益**：左栏高级卡只剩 2 个开关（覆盖/严格）+ 2 个下拉（硬件加速/解码模式，且已建议合并为 1 个）；表格少一列子行；执行看板去掉一个指标；全屏蒙层消失。

### 6.4 脏状态机制应该大幅简化

当前 **11 个圆点 + 9 个单项撤销 + 2 个"还原 N 项"** 是全案最重的加法。按 §6.1 标准评估："哪些参数被改过"命中"对照"一条（执行前需确认），**不命中频次与后果**——因为改动本身是用户主动行为，他大概率记得。

**建议简化方案（保留价值、去掉 20 个元素）**：

| 现状 | 建议 |
| :--- | :--- |
| 11 个字段级脏点（`.dot-dirty`） | **保留**（成本低、信息密度高，是"哪项被改"的最轻量表达） |
| 9 个单项撤销按钮（`.undo-btn` ↺） | **删除**，改为折叠头一个"恢复预设默认" |
| 2 个"还原 N 项"链接（`btnResetVideo/Audio`） | **合并为 1 个**：折叠头右侧"已微调 N 项 · 恢复默认" |
| 折叠头摘要 | **保留**（如 `HEVC · 1920p · CRF 23`，这是最高价值的部分） |

**简化后**：每个折叠卡片头 = `标题 + 生效摘要 + 脏点 + "已微调 N 项 · 恢复默认"`。**从 22 个交互元素降到 8 个**（3 卡片 × 2 + 2），且核心信息（改了没有、改了几项、一键还原）全部保留。

### 6.5 建议的最终主面板结构

```
┌───────────────────────────────────────────────────────────────┐
│ 顶栏 品牌 / ffmpeg 状态 / GPU 徽章 / [引擎运行态胶囊] / 日志 / 侧栏 / 设置 │
├────────────────────┬──────────────────────────────────────────┤
│ 左栏（380px，可收起）│ 右栏主工作区                              │
│                    │ 工具栏 [生成计划/更新计划] [开始转码] [终止] [清空] │
│ 1 输入与输出        │        ……………… 右侧：N 个任务 · 总大小 · 总时长   │
│   · 投放区          │ ┌──────────────────────────────────────┐ │
│   · 清单            │ │ 任务表（7 列）                        │ │
│   · 输出目录/模式    │ │ 多选/#/源文件/目标文件/编码转换/状态/操作 │ │
│   · 前缀后缀        │ │ （空态：一行提示 + 选择文件按钮）        │ │
│ 2 预设（含指标摘要） │ └──────────────────────────────────────┘ │
│ 3 视频微调（折叠）   │ 执行看板：总进度 / 当前文件 / 速度 / ETA     │
│ 4 音频微调（折叠）   │ （完成时：结果计数 + 打开输出目录）          │
│ 5 高级（折叠）       │                                          │
│   · 硬件加速（合并） │                                          │
│   · 覆盖/严格        │                                          │
├────────────────────┴──────────────────────────────────────────┤
│ 按需抽屉：任务检查器（详情/命令/单任务日志） · 运行日志           │
└───────────────────────────────────────────────────────────────┘
```

**与现状的差异**：左栏 5 卡不变但高级卡内容减半；表格 9 列 → 7 列；执行看板去 FPS；全域蒙层删除；Hero 画板简化；脏状态从 22 元素降到 8 元素。

### 6.6 一句话回答用户

> **主面板 = 输入 + 输出 + 预设 + 计划/执行按钮 + 任务表 + 进度 + 失败处置，共 7 项，其余全部下沉。**
>
> **"次要设置做弹窗"的直觉方向对，但要分清两类**：**系统级配置**（工具路径、GPU、主题）→ **弹窗**（现状已做对）；**不常用的转码参数**（音频微调、命名）→ **折叠卡片而非弹窗**（因为批量转码需要反复对照，弹窗会打断循环，这也是 HandBrake 等主流的做法）。
>
> **真正该砍的不是"要不要弹窗"，而是那些"既不该常驻、也不该弹窗"的项**——`jobs`、删除源、FPS、解码器细节，它们应该**直接删除或下沉到检查器**（§6.3）。

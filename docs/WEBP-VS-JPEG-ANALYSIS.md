# WebP 与 JPEG 编码特性、性能及元数据实测分析报告

本报告基于当前开发环境（Node.js、sharp / libvips、libjpeg-turbo、mozjpeg、libwebp、ExifTool）对 WebP 与 JPEG 在不同质量参数、图像类型、转码性能及元数据维度的实测数据进行汇总与分析。

### 2. 等效视觉质量对标（WebP Q70 对标 JPEG Q80）

在主观肉眼检视（100% 原始像素下比对睫毛、唇纹、毛发与眼球倒影）中：
- `WebP Q70` 的细节保留度与伪影抑制能力整体等同于甚至略好于 `JPEG Q80`。
- 将二者进行同效体积对比：
  - **4K 人像（p2，3840×2560）**：
    - JPEG Q80（MozJPEG）：`820.5 KB`
    - JPEG Q80（libjpeg-turbo）：`923.9 KB`
    - WebP Q70（effort=4）：`261.9 KB`
    - **体积缩减率**：从 820.5 KB 降至 261.9 KB，**体积缩减 68.1%**（仅为原 JPEG 的 31.9%）。
  - **2400 万像素人像原图（6000×4000）**：
    - JPEG Q80（MozJPEG）：`2290.9 KB (2.24 MB)`
    - JPEG Q80（libjpeg-turbo）：`2642.1 KB (2.58 MB)`
    - WebP Q70（effort=4）：`1008.6 KB (0.98 MB)`
    - **体积缩减率**：从 2.24 MB 降至 0.98 MB，**体积缩减 56.0%**。

## 三、 失真伪影形态与算法差异

| 比较维度 | JPEG (DCT 架构) | WebP (VP8 帧内预测架构) |
| :--- | :--- | :--- |
| **核心变换单元** | 固定 8×8 离散余弦变换（DCT）块 | 4×4 或 16×16 宏块（内含 Walsh-Hadamard 变换及 DCT） |
| **低质量区失真形态 (Q40~Q55)** | **离散方块伪影 (Blocking)**：图像出现明显网格；<br>**蚊式噪点 (Ringing)**：在高对比边缘（如睫毛、眼线）周围散落杂乱斑点；<br>**色阶断层 (Contouring)**：平滑肤色过渡区出现等高线阶梯。 | **平滑软化 (Smoothing)**：无方块感，轮廓保持完整；<br>**高频纹理滤除**：极细绒毛与毛孔被抹平，主观呈轻微“磨皮”观感；<br>平滑渐变区色阶过渡连贯。 |
| **中高质量区形态 (Q70~Q75)** | 8×8 宏块消除，边缘噪点减弱，暗部仍存在少量量化杂波。 | 睫毛、瞳孔高光、发丝纹理完全还原，色阶过渡平滑。 |
| **色度抽样支持** | 支持 `4:2:0`、`4:2:2`、`4:4:4`。 | **有损规范强制为 YUV 4:2:0**。<br>包含锐利红蓝文字/图表时需依赖 `smartSubsample`（`-sharp_yuv`）减轻边缘溢色。 |

## 四、 编码耗时与吞吐量基准测试（Benchmark）

测试环境为单机多线程（sharp 底层线程池），对 4K 图像（3840×2560，9.8 MP）与 2400 万像素图像（6000×4000，24 MP）分别进行多次迭代测试取平均值：

### 表 4-2：全尺寸原图（6000×4000，24 MP）转码耗时实测
| 编码配置 | 质量 (Q) | 耗时 (ms/图) | 吞吐量 (MP/s) | 输出大小 (KB) | 相对 JPG Q80 体积 |
| :--- | :---: | :---: | :---: | :---: | :---: |

| **WebP (effort=5 高压缩)** | Q70 | **4242.0** | **5.7** | 965.8 (0.94 MB) | **-63.4%** |

### 耗时归因与结论：
1. **libjpeg-turbo 具备绝对吞吐优势**：
   - 依赖极简的 8×8 独立块计算与完整的 AVX2/SIMD 汇编优化，处理速度达 140~150 MP/s（4K 图仅需约 70ms）。
2. **MozJPEG 与 WebP 耗时处于同一数量级**：
   - MozJPEG 因启用网格量化（Trellis）与动态规划霍夫曼优化，耗时比 libjpeg-turbo 增加 7~10 倍（4K 耗时 ~540ms）。
   - WebP 默认档位（`effort: 4`）耗时为 ~670ms，与 MozJPEG 接近；但在相近耗时下，WebP 产出体积仅为 MozJPEG 的 32%。
3. **WebP `effort` 存在显著边际效益递减**：
   - `effort: 4` $\rightarrow$ `effort: 5`：耗时增加 104%（从 671ms 增至 1370ms），体积仅额外减少 12.2 KB（不到 4.7%）。
   - 生产环境中离线构建建议固定为 `effort: 4`；实时在线服务建议选用 `effort: 2`（耗时仅 253ms，吞吐量提升 2.6 倍）。

## 五、 元数据（EXIF / XMP / IPTC / ICC）支持实测

使用 ExifTool 对相机直出图、Lightroom 导出图分别转码后的输出文件进行逐项结构性比对：

### 1. 容器结构对照
- **JPEG**：采用 JFIF 段结构，通过 `APP1`（`0xFFE1`）存储 EXIF 与 XMP，`APP2`（`0xFFE2`）存储 ICCP，`APP13`（`0xFFED`）存储 Photoshop IRB / IPTC。
- **WebP**：采用 RIFF 容器规范，元数据均以独立数据块存储：
  - `VP8X` 块：10 字节扩展头部，置位元数据 Flag 比特。
  - `EXIF` 块：TIFF 格式元数据。
  - `XMP ` 块：XML 封包。
  - `ICCP` 块：色彩配置文件。

### 2. 字段保留实测结果

#### 表 5-1：关键业务与硬件字段保留对照
| 字段名称 | 业务含义 | 原图 | 转出 JPG | 转出 WebP | 一致性状态 |
| :--- | :--- | :---: | :---: | :---: | :---: |
| `Make` / `Model` | 相机品牌与型号 (如 SONY ILCE-6300) | 有 | 保留 | 保留 | 严格一致 |
| `LensModel` | 镜头型号 (如 E 18-135mm F3.5-5.6 OSS) | 有 | 保留 | 保留 | 严格一致 |
| `DateTimeOriginal` | 原始拍摄时间戳 (含时区 +08:00) | 有 | 保留 | 保留 | 严格一致 |
| `ExposureTime` / `FNumber` | 快门速度、光圈值 | 有 | 保留 | 保留 | 严格一致 |
| `ISO` / `FocalLength` | 感光度、焦距 | 有 | 保留 | 保留 | 严格一致 |
| `GPSLatitude` / `GPSLongitude` | 拍摄地经纬度浮点值 | 有 | 保留 | 保留 | 精度严格一致 |
| `GPSAltitude` | 海拔高度 | 有 | 保留 | 保留 | 严格一致 |
| `ColorSpace` / `ICCP` | 色彩空间定义 (如 sRGB / Display P3) | 有 | 保留 | 保留 | 严格一致 |
| `Orientation` | 旋转方向标记位 | 有 | 保留 | 保留 | 严格一致 |
| `Artist` / `Copyright` | 拍摄作者、版权声明文本 | 有 | 保留 | 保留 | 严格一致 |
| `Software` | 原始处理软件标记 | 有 | 保留 | 保留 | 严格一致 |

#### 表 5-2：差异字段分析
在包含 Lightroom 导出的样本中，比对显示仅有 14 项字段在 JPG 中存在而在 WebP 中缺失：
- **缺失字段列表**：`DisplayedUnitsX`, `DisplayedUnitsY`, `CurrentIPTCDigest`, `CodedCharacterSet`, `ApplicationRecordVersion`, `TimeCreated`, `DigitalCreationDate`, `DigitalCreationTime`, `By-line`, `CopyrightNotice`, `PhotoshopThumbnail`, `IPTCDigest`, `DateTimeCreated`, `DigitalCreationDateTime`。
- **差异归因**：上述字段均属于 1990 年代陈旧的 **IPTC-IIM (Photoshop APP13 IRB)** 格式及 Photoshop 内置位图缩略图。WebP RIFF 规范只接受标准的 `EXIF` 与 `XMP ` 块，不承载该私有格式。由于作者、版权与时间信息在 `XMP ` 与 `EXIF` 中均有对应标准副本，因此**无任何实质信息丢失**。

### 3. 保留全量元数据下的最终文件大小对比
以 `DSC_20260403_105740_1632.jpg` 为例，转出 WebP 文件总大小为 1,895,628 字节，二进制数据块构成如下：
- `VP8 `（图像流）：1,868,328 字节（~1.78 MB）
- `EXIF`（硬件元数据）：14,286 字节（~14.0 KB）
- `XMP `（Adobe 调色配置）：12,471 字节（~12.2 KB）
- `ICCP`（色彩配置）：480 字节
- `VP8X`（扩展头）：10 字节

在保留全量 EXIF + XMP 的前提下：
- **原片**：8.75 MB
- **转出 JPG (Q85)**：3.67 MB
- **转出 WebP (Q75)**：1.81 MB（**较同源 JPG 减小 50.7%**）

## 六、 生产环境选型建议与配置参考

### 1. 业务场景决策矩阵
| 业务场景 | 格式与核心参数建议 | 4K 耗时 | 体积表现 | 决策权衡 |
| :--- | :--- | :---: | :---: | :--- |
| **在线高并发 / 动态缩放代理** | WebP `quality: 70`, `effort: 2` | ~250 ms | 极小 (~280 KB) | 压低 CPU 占用与响应延迟，吞吐量比默认提升 2.6 倍，体积依然较 JPG 缩减 68%。 |
| **离线批量构建 / 静态 CDN 发布** | WebP `quality: 75`, `effort: 4`, `smartSubsample: true` | ~690 ms | 极小 (~320 KB) | 取得画质还原与体积节约的最优平衡点。 |
| **高吞吐连拍存储 / 内部归档导出** | JPEG `quality: 80`, `mozjpeg: false` | ~70 ms | 中等 (~920 KB) | 极速导出，单核跑满 140+ MP/s，但占用较多磁盘与带宽。 |

### 2. Node.js (sharp) 推荐调用示例

```javascript
import sharp from "sharp";

// 场景 A：静态 CDN 资产离线构建（高画质、全元数据、平衡算力）
await sharp(inputPath)
  .rotate() // 纠正 EXIF 方向并重置标记位
  .withMetadata() // 完整保留 EXIF、XMP 及 ICC 色彩空间
  .webp({
    quality: 75,
    effort: 4, // 官方推荐平衡点，勿盲目使用 5 或 6
    smartSubsample: true, // 改善高反差边缘与文字溢色
  })
  .toFile(outputPath);

// 场景 B：在线高并发服务（优先保障吞吐与响应延迟）
await sharp(inputBuffer)
  .resize({ width: 1920, withoutEnlargement: true })
  .webp({
    quality: 70,
    effort: 2, // 快速模式，单图 CPU 耗时降低 60%
  })
  .toBuffer();
```

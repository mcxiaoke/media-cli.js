- **P2-5** 极短素材（<~30 帧）纯 CPU 更快（线性拟合：cuda 359+1.05N，

## 23:00 10bit 源 + h264 目标的位深对齐（scale 的 format=nv12，全硬解 0 拷贝）

承接 22:40 的 swdec 层，补齐「硬件解码能过但硬件编码器打不开 10bit」这一档。

### 问题

`h264_nvenc` / `h264_qsv` **不吃 10bit 输入**：`-h encoder=h264_nvenc` 的格式列表里
虽列出 `p010le`，但驱动不支持，报 `Error while opening encoder` / `Nothing was written
into output file`。于是「10bit 源 + h264 预设」在本次改造前**整链探测失败 → 落 libx264**
（即便 NVDEC/QSV 能硬解、NVENC/QSV 能编 8bit h264）。

### 解法与实测依据（三种写法的差异）

把 10bit→8bit 的转换放进 **scale 滤镜的 `format=` 选项**：

| 写法 | 结果 |
| --- | --- |
| `scale_cuda=w=..:h=..:interp_algo=lanczos:format=nv12` | ✅ 输出仍是**硬件帧**（sw_format 变 nv12）→ **0 拷贝** |
| `-vf "scale_cuda=..,format=nv12"`（逗号=独立 format 滤镜） | ❌ 要求出显存 → `Impossible to convert between the formats` |
| `-pix_fmt nv12`（输出选项） | ❌ 同样要求出显存 → 失败 |
| `scale_cuda=…:format=cuda`（把 hw 格式名当 scale 的选项） | ❌ `Unsupported output format: cuda`（scale 的 format 只接软件格式名） |

「仍是硬件帧」的两条硬证据：输出可再接一个 `scale_cuda`；输出可被 `hwdownload,format=nv12`
成功下载（`hwdownload` 只接受硬件帧）。性能实测（4K→1080p，h264_nvenc）：`:format=nv12`
**16.5x ≈ 0 拷贝基准 16.3x**，而 2 拷贝路径 6.92x —— 即**无损**。

### 改动

- `lib/hwaccel.js`
  - 新增 `scaleFormatOverride(tier, { codecFamily, pixFmt, bitDepth })`：仅当
    `tier ∈ {cuda, qsv}` 且 `codecFamily === h264` 且源为 10bit（`bitDepthOf` 兼容
    ffprobe 内嵌位深与 mediainfo 独立 BitDepth）时返回 `"nv12"`。
    d3d/swdec/cpu 层帧本就在系统内存（由 `-pix_fmt` 对齐）；hevc 族编码器可直接吃 p010/p012。
  - `buildScaleFilter(tier, size, swFormat)`：按逗号拆分 `filterArgs` —— 选项段参与拼接、
    尾部独立滤镜（cuda 层的 `,format=cuda`）原样保留；`swFormat` 并入选项段。
    `size` 为 null 时只做格式对齐（w/h 缺省 = iw/ih），用于「任务不需要缩放但仍需对齐」。
  - `buildVideoFilters(...)`：新增 `codecFamily/pixFmt/bitDepth`，需要对齐时**即使无缩放也输出**
    （实测 1:1 对齐成本 ~1%：36.7x vs 37.1x）。无缩放且无对齐需求时行为不变（不输出滤镜）。
  - `buildLayerArgs` 转发 `bitDepth`；`probeLayer` 的 `buildProbeArgs` 也补上 `bitDepth`
    —— 缺它时探测按未对齐链跑，结论与真实命令不一致（mediainfo 的 pixelFormat 不含位深）。
- `lib/ffmpeg_build.js`

    `buildFilterArgs` 的 «是否输出 `-vf`» 条件加入它 —— 否则「无需缩放/改帧率/无用户滤镜」
    的任务会整段跳过缩波段、连带丢掉位深对齐（本次 e2e 实测到的缺口）。
  - `buildScaleFiltersFromPlan` / `resolveComplexFilterScale` 传入
    `codecFamily/pixFmt/bitDepth`，与探测侧同源。

## 22:40 新增 swdec 层：硬解不可用时「CPU 解码 + CPU scale + 硬件编码」

基于当天三份实测（硬解矩阵、通道交叉统计、混合链计时，见
`docs/ffmpeg/ffmpeg-hwaccel-support-matrix-20260921.md`）固化的链路决策改造。

### 结论依据（实测，720p→360p，h264_nvenc）

| 链路 | 跨 PCIe 拷贝 | 吞吐 |
| --- | --- | --- |
| 硬解 + 硬件 scale + 硬编（全 GPU） | 0 | **39.1x** |
| 硬解 + 下载 + CPU scale + 硬编 | 2 | 17.1x |
| **软解 + CPU scale + 硬编（本层形态）** | 1 | **27.7x** |
| 纯软全链 libx264 | 1 | 10.9x |

- 「帧在哪解码，filter 就放哪」：硬解不可用时**不加 `-hwaccel`** 才是最省拷贝的形态；
  「半吊子硬解」比纯软解还慢（17.1x < 25.1x）。
- 旧行为：GPU 解码层被拦下 → 直接落 `cpu` 层 → **libx264/libx265**（10.9x），
  白白丢掉硬件编码（27.7x）。

### 1. 新增 `swdec` 层（lib/hwaccel.js TIERS）

- 层定义：`hwaccel: null`、`hwFormat: null`、`filter: "scale"`（CPU scale）——与 `cpu` 层
  参数一致，**唯一差异是编码器走硬件**。实测依据：含 `-hwaccel` 会把帧下载回内存（2 次拷贝），
  故本层**不启用任何硬件解码**。
- 编码器行按主 GPU 厂商注入：`resolveTiers` 用 `primaryVendor(caps)` 从
  `hwdetect.SWDEC_ENCODERS_BY_VENDOR`（nvidia→nvenc / intel→qsv / amd→amf）取行挂到
  `tier.encoderRow`；拿不到厂商行时退回 `ENCODER_MATRIX.cpu`（等价旧行为，不会更差）。
  层名保持单一（`swdec`），不把厂商维度泄漏到候选链或 `--hwaccel` 值域。
- `buildEncoderArgs` / `pickEncoder` 接受可选 `tier` 参数并优先用 `tier.encoderRow`；
  `buildLayerArgs`、`ffmpeg_build.buildVideoArgsFromPlan` 透传 `tier`
  （探测命令与真实命令必须走同一解析路径）。

### 2. 质量值改按「实际编码器」换算（lib/hwaccel.js）

`buildEncoderArgs` 的质量偏移从 `normalizeQuality(tierName, …)` 改为
`normalizeQualityForEncoder(encoder, …)`。对既有层**等价**（cuda/d3d→h264_nvenc→nvenc、
qsv→qsv、amf→amf、cpu→libx264→x264、vp9 回退 libvpx-vp9→x264 基准），对 `swdec` 必需
（编码器随厂商变化，按层名查表会恒取兜底键）。

### 3. `swdec` 位深对齐：10bit 源 + h264 目标注入 `-pix_fmt yuv420p`

实测 `h264_nvenc` **不吃 10bit 输入**（`-h encoder=h264_nvenc` 虽列出 `p010le`，但驱动不支持，
报 `Nothing was written into output file`）。不加则整层探测失败 → 白落 libx264。
`swdec` 层帧本就在系统内存，`-pix_fmt` 只插一次 CPU 格式转换，无下载代价；hevc 族不注入
（`hevc_nvenc`/`hevc_qsv` 可直接吃 p010）。

### 4. 链路接线（lib/hwdetect.js / ffmpeg_build.js / ffmpeg_run.js）

- `candidateTiers` auto 链：`swdec` 插在**厂商解码层之后、`cpu` 之前**；
  入场条件 = 本机确实存在该厂商的硬件编码器（`caps.encoders` 实测集，与解码能力无关）。
  旧 caps 无 `encoders` 字段时不插入（向后兼容）。`decode-mode cpu` 与显式 `--hwaccel X`
  的链**不加 swdec**（保留用户的显式全软/显式层意图）。
- `strict` 模式的「硬件层」判定由 `t.name !== "cpu"` 改为 `t.hwaccel` —— `swdec` 是
  「CPU 解码 + 硬件编码」，不满足 strict 要求的硬件*解码*。
- 软解层判定（`hwupload_cuda` 前置条件）：`=== "cpu"` 扩为 `["cpu","swdec"]`，
  否则 `swdec` + 用户 CUDA 滤镜链会缺上传而失败。
- 日志标签新增 `[SW+HW]`（lib/ffmpeg_run.js `tierBadge`）：swdec 既非全程硬件也非全软，
  统一收敛到一处，避免把「有硬件编码」误报成 `[SW]`。

`systeminformation`（v5.33.13，MIT、零运行时依赖，实测 graphics() 于本机 822ms 返回 3 块 GPU），把「GPU 型号 → 编解码支持矩阵」结构化接入硬件探测链路。

### 1. `lib/gpu.js`（新建，纯数据 + 纯函数，可独立测试）

- **GPU 探测**：`detectGpus()` 封装
  `systeminformation.graphics()`，vendor 归一化（nvidia/amd/intel/other），NVIDIA 型号解析为代次；探测失败降级返回
  `[]`，不影响 ffmpeg 侧探测。
- **型号 → 代次**：`nvidiaGenerationOf()` 覆盖 RTX 50xx → gen50(Blackwell)、RTX 40xx →
  gen40(Ada)、RTX 30xx → gen30(Ampere)、RTX 2050 →
  **gen30 特例**（名义 20 系、硅片 Ampere，能力等同 30 系）、RTX 20xx / GTX 16xx →
  gen20(Turing)、GTX 10xx → gen10(Pascal)。
- **支持矩阵**：`NVENC_MATRIX`（编码）与
  `NVDEC_MATRIX`（解码），单元格取值 yes/no/partial，数据来源为报告四张统计表（含口径提醒：GTX16 的 HEVC
  B 帧 partial、HEVC 4:4:4 解码 20 系起支持、AV1 解码 20 系 partial 来自 RTX 2050 等）。
- **预探测列表**：`gpuProbeList(gpus)` 以主 NVIDIA GPU 代次生成
  `{decode:[{codec,chroma,bitDepth,support}], encode:[{codec,format,support}]}`，无 NVIDIA GPU
  / 未知代次返回 null（不预筛）。
- **查询函数**：`nvdecSupportOf(gen, codec, pixFmt, bitDepth)` /
  `nvencSupportOf(gen, codec, format)`，配合 `chromaOfPixFmt` / `bitDepthOfPixFmt` /
  `normalizeDecodeCodec` 解析 ffprobe 与 mediainfo 两种像素格式口径。

### 2. `lib/hwdetect.js`：探测并入 caps

- `detectHardwareCapabilities` 在静态能力探测的同时**并行**执行
  `detectGpus()`，失败不影响既有 ffmpeg 探测；caps 新增 `gpus`（GPU 列表）与
  `gpuProbe`（预探测列表）。
- `logEnvironment` 输出 `gpus=[nvidia:RTX 4070(gen40)/intel:UHD 750/...]` 与预探测列表条目数。

### 3. `lib/hwaccel.js`：selectTier 解码预筛（gpuBlocksDecode）

- auto 降级链对 cuda / d3d 层做**解码矩阵预筛**：只有 NVIDIA 主 GPU 支持矩阵**明确 no**
  的组合（如 40 系 + H.264 4:2:2 / HEVC
  4:2:2 高位深）跳过 ffmpeg 干跑，直接视为该层探测失败继续降级——结论与真实探测等价，省去必然失败的探测。
- ⚠️ 收紧规则（保证行为不回归）：partial / unknown
  / 无矩阵数据一律放行；qsv(Intel)/amf(AMD) 等厂商层不套 NVIDIA 矩阵；strict 模式与 gpu 模式（显式指定层）不预筛，仍由真实探测兜底裁决。

## 18:50 Phase 4（T5）：硬件加速自动适配修复（lib/hwaccel.js + lib/hwdetect.js + lib/ffmpeg_run.js）

在 Phase
1-3（YAML 预设单源化、滤镜三段式、显式 encoder/decoder 指定）基础上，修复自动适配层的四处缺陷：

### 1. auto 候选链移除 d3d 层（`lib/hwdetect.js` candidateTiers）

- **变更**：auto 默认链从「厂商专属层 → d3d → cpu」改为「厂商专属层 → cpu」，`caps.usable.d3d`
  不再自动入链。d3d 是「任意厂商 d3d11va 解码 +
  NVENC 编码」的混合层，auto 语义下对多数机器都不是最优解（AMD/Intel 机器上 nvenc 编码器不存在）。
- **显式指定仍可覆盖**：`--hwaccel d3d/d3d11va/d3d12va` 白名单分支与 `--decode-mode gpu`
  不受影响，归一化到 d3d 层后照常使用（白名单层可用 → `[d3d, cpu]`，gpu 模式 →
  `[d3d]`）。逐层探测兜底不变。

### 2. 静态滤镜预筛（`lib/hwdetect.js` candidateTiers 消费 caps.filterSupport）

- **变更**：auto 默认链对厂商层做静态预筛——该层的缩放滤镜必须被当前 ffmpeg 构建支持（cuda→`scale_cuda`、qsv→`scale_qsv`、amf→`vpp_amf`），滤镜缺失则该层不进候选链（warn 记录跳过原因）。此前老构建缺
  `scale_cuda`/`vpp_amf` 时该层总被尝试、probe 必然失败，白白多一次干跑。
- **范围**：仅 auto 默认链；显式白名单 / gpu 模式不预筛（用户明确指定时由探测兜底裁决）。

### 3. codecFamily 扩展 av1/vp9 + ENCODER_MATRIX 补行（`lib/hwaccel.js`）

- `codecFamilyOf`：识别 `/av1|av01/` → `av1`、`/vp9|vp09/` →
  `vp9`（置于 hevc 判定的 hevc/h265/x265/hvc1 之前； `av01`/`vp09`
  是 ffprobe 的短名）。`codecFamilyOfPreset` 随之支持 `--video-codec av1_nvenc`、
  `videoCodecFamily: av1/vp9`。
- `ENCODER_MATRIX` 补行（依据 docs/ffmpeg/ffmpeg-guide-hwaccel-compat.md 的编码器可用性）：
    - cuda/d3d：`av1 → av1_nvenc`（**无 vp9_nvenc**，键缺）
    - qsv：`av1 → av1_qsv`、`vp9 → vp9_qsv`
    - amf：`av1 → av1_amf`（**无 vp9_amf 编码器**，键缺）
    - cpu：`av1 → libaom-av1`、`vp9 → libvpx-vp9`（libsvtav1 不随 ffmpeg 主构建分发，本机实测无；libaom-av1 是随包可用的保守默认，质量优先）
- **矩阵缺失 fallback**：某层缺该族硬件编码器（cuda/vp9、amf/vp9）时 `buildEncoderArgs` 回退
  `ENCODER_MATRIX.cpu`（libvpx-vp9）——编码走 CPU，但解码仍走该层硬件（层只决定解码路径）。

### 4. 探测与真实命令强同源修正（lib/hwaccel.js + lib/ffmpeg_run.js）

- **bitrateK 透传**：`resolveHwPlan` → `selectTier` → `probeLayer` → `buildProbeArgs` →
  `buildLayerArgs` 全程透传 `entry.dstArgs.videoBitrateK`（真实命令带 `-maxrate/-bufsize`
  时探测也带，避免码控参数改变编码行为导致探测结论与真实不一致）。
- **probeCacheKey 补 speed/framerate**：speed≠1 或 framerate 非空时滤镜链含 setpts/fps，缺键会让「带滤镜」与「不带滤镜」的探测结果互相复用而误判。
- **质量参数按实际编码器分发**：`buildEncoderArgs` 由 `tierImpl(tierName)` 改为
  `encoderCalibImpl(encoder)`（按实际编码器名判实现）。此前 cuda/amf 层 vp9 回退 libvpx-vp9 时会错给 nvenc/amf 参数，CPU 编码器不认；现统一按编码器实现走 cpu 分支（-crf）。
- **CPU av1/vp9 纯 CRF 补 `-b:v 0`**：libaom-av1 / libvpx-vp9 必须 `-b:v 0` 才走纯 CRF，否则 `-crf`
  无效（docs/ffmpeg/ffmpeg-guide-encoders.md 11.1「-crf 无效」条目）。

### 相关文件

- `lib/hwaccel.js`：ENCODER_MATRIX、codecFamilyOf、buildEncoderArgs（fallback + 实现分发 + -b:v
  0）、probeCacheKey、probeLayer、selectTier（bitrateK 透传）；删除不再使用的 tierImpl。
- `lib/hwdetect.js`：candidateTiers（d3d 移除 + FILTER_SUPPORT_KEY 静态预筛）。
- `lib/ffmpeg_run.js`：resolveHwPlan 传 `entry.dstArgs.videoBitrateK` 进 selectTier。

## 16:30 新增：ffmpeg --strict 严格模式（探测不支持即跳过该文件，默认关闭保持兼容）

按确认的语义落地严格模式：**prepare/plan 阶段探测到软件或硬件不支持时，warn 日志 + 跳过该文件**，跳过文件**不进入 confirm 重试名单、不会真正走到 run
ffmpeg 阶段**，其余文件继续，EXIT=0；不再自动降级、也不整体报错退出。`--strict`
为布尔开关，**默认 false**（保持既有兼容行为），仅显式传入才启用严格模式。

### 严格模式各探测路径

- **H264 10bit**（`cmd/cmd_ffmpeg.js` prepare）：Nvidia/Intel 均无 10bit H264 硬解，strict 下
  `Skip[Strict10bit]` + warn + 跳过（不再静默切软解）。
- **音频编码器缺失**（`cmd/cmd_ffmpeg.js`
  prepare 预检）：预设指定了本机构建不支持的编码器（如缺 libfdk_aac 的版本用到 `-c:a libfdk_aac`）→
  `Skip[StrictCodec]` + 跳过，失败在 prepare 拦截、不拖到 confirm/run 阶段。
- **硬件层不可用**（`lib/hwaccel.js` selectTier + `lib/ffmpeg_run.js`
  run 阶段 catch）：strict 下只尝试第一候选硬件层，失败即 `Skip[Strict]` +
  `entry.skipped = true`（不设
  `ffmpegFailed`，自动不进 confirm 重试名单、不真正执行 ffmpeg）；候选链全为 cpu 时同样抛错，提示用
  `--decode-mode cpu` 显式指定软解。
- **run 阶段 CPU 降级重试**（`cmd/cmd_ffmpeg.js`
  runFFmpegTasks）：strict 下失败不再询问 CPU 重试，warn `ffmpeg.strict.retry` 后跳过。

### 汇总与日志

- `runFFmpegTasks` 结果汇总加入 `skipped=` 计数（含无跳过时不输出，保证日志兼容）；逐文件落盘
  `Skip[Strict] <path> 原因`。
- `lib/i18n.js`：新增 `ffmpeg.strict` / `.strict.hw` / `.strict.audio` / `.strict.retry` /
  `.strict.10bit` / `.strict.skip.count` 中英文案，strict 语义文案统一为「跳过该文件」。

## 16:10 新增：FFmpeg 二进制定位统一（lib/ffmpeg_bin.js）+ 能力探测去重

同一批改动顺带解决「探测与执行用的不是同一个 ffmpeg」的不一致问题：

- **`lib/ffmpeg_bin.js`（新建）`resolveFFmpegBinary()`**：定位优先级 `FFMPEG_PATH` → `FFMPEG_BINARY`
  →
  `which("ffmpeg")`，环境变量指向的文件**实际存在**才采用，否则继续往下找；解决「PATH 里无 fdk 的版本排在 nonfree 版之前」导致探测/执行结果不一致的问题。
- **`lib/ffmpeg_run.js`** `executeFFmpeg` 改执行 `ffmpegPath || "ffmpeg"`（探测与执行同一二进制）。
- **`lib/hwdetect.js`**：in-flight promise 去重（prepare 阶段多任务并发预检时只实际探测一次）；新增
  `parseVersionInfo` 解析 `ffmpeg -version` 的版本与 configuration 串，随探测打印环境信息。
- **`lib/ffmpeg_build.js`** `buildAudioArgs` 接入 caps：非 strict 下音频编码器不可用时**静态降级**
  `libfdk_aac → aac`（预览命令结构即与真实执行一致）；strict 下 `fallbackAudioEncoder`
  不降级原样返回（拦截职责在 prepare 预检）。导出 `fallbackAudioEncoder` 纯函数。

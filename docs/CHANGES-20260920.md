## 21:15 修复：探测缓存键缺少位深，10bit 源被误选硬件层而编码失败

背景：`F:\Temp\testvideos` 全量转码测试（`h264_2kl` 预设）中，10bit VP9/AV1 源
（如 bear-320x180-hi10p-vp9、Jellyfin AV1 HDR10）在 cuda/qsv 层报
`Error while opening encoder` 失败，CPU 重试成功 —— 分层探测没有把这些文件降级到 cpu。

根因（用当前代码复现确认）：`probeCacheKey` 声明「按 层|编码|位深|像素格式|尺寸 缓存」，
但实现漏了**位深**。mediainfo 提供的 `pixelFormat` 是 "ColorSpace+ChromaSubsampling"
（如 "YUV4:2:0"），8bit 与 10bit 源值相同 → 同键 → 8bit 文件探测 cuda 通过后，
10bit 文件直接复用结果误选 cuda → h264_nvenc/h264_qsv 只支持 8bit，编码器打不开。
实测复现：8bit HEVC 缓存 OK 后，`hevc_4k25P_main10_2`（10bit）被选中 cuda 层。

- **lib/hwaccel.js**：`probeCacheKey` 增加 `bitDepth` 参与键值；`probeLayer`/`selectTier`
  透传 `bitDepth`。
- **cmd/cmd_ffmpeg.js**：`resolveHwPlan` 调 `selectTier` 时传入 `ivideo.bitDepth`。
- **lib/media_parser.js**：mediainfo 路径 `pixelFormat` 在 ColorSpace 为空时回退用
  `ChromaSubsampling`（VP9 等 420/422/444 此前同为空串，探测键互相污染）。
- 验证：当前代码复现脚本显示修复前 10bit HEVC → cuda（会失败）、修复后 → cpu；
  `npm run check` 与 ESLint 通过。日志中 4:2:2/4:4:4 源（Error reinitializing filters）
  同属该机制。

## 20:45 修复：QSV 质量参数改用 -global_quality（ICQ 码控）

调查结论：`lib/hwaccel.js` 此前对 qsv 用 `-q:v`（qscale flag → CQP 固定 QP），注释声称

**CQP 模式专属**：`-q:v 18` 在 4K 10bit 源 @1080p 输出暴涨到 13.6MB，而 `-global_quality 18`
仅 1.0MB 且 18/20/24/28 严格单调。

- **lib/hwaccel.js**：`buildEncoderArgs` qsv 分支 `-q:v` → `-global_quality`；移除
  `QSV_10BIT_MIN_Q` 钳制及 `normalizeQuality` 中的 10bit 钳制逻辑（ICQ 已消除该异常，
  钳制反而会损害 10bit 源画质）；修正质量参数实测注释。
- **cmd/cmd_ffmpeg.js**：修正 `buildVideoArgsFromPlan` 中「qsv 必须用 -q:v」的错误注释。
- **lib/ffmpeg_presets.js**：注释中 qsv 质量参数名改为 `-global_quality`。
- 验证：`npm run check` 与 ESLint 通过；qsv/cuda/cpu 参数生成与端到端真实编码均验证。

  **仅凭集合差就整目录移入回收站**，未校验目录确实为空：移动失败残留的文件、以及未纳入扫描的非媒体文件（`.txt`/`.nfo`/`.db`）会随目录一起被搬走。→ 删除前
  `readdir` 确认空，非空/不可读的一律保留并列出样本。

### P1-3 解压安全

- **Zip bomb**：条目声明的 `uncompressedSize`
  来自包内头部，完全不可信，而原先唯一的 2GB 保护已被注释掉。新增「绝对上限 20GB + 压缩比上限 200×」双判据（小 zip 至少允许解出 100MB，避免误伤高压缩比文本），超限时中止整个压缩包并清理临时文件。
- `--override` 此前走 `fs.remove` **硬删除**且无二次确认 → 改为 `safeRemove`
  移入回收目录（误操作可找回）；失败则中止，绝不带着残留继续解压。

### P1-4 `rename` 同批重名检测是死分支

- `cmd/cmd_rename.js` 的 `seenPaths` 全文件**无任何 `.add()`**，`:774`
  分支永不成立。同批两个源文件映射到同一目标名时，因尚未落盘 `fs.pathExists`
  查不到，后一个会**覆盖**前一个，且 dry-run 预览与实际执行结果不一致。→ 在 `outPath` 赋值处补
  `seenPaths.add(newPath)`。

### P1-6 `cmd_ffmpeg` 死分支与残留

- `--decode-mode cpu` / H264 10bit 只写入 `useCPUDecode`，而 `createFFmpegArgs` 只读 `useCUDA`
  → 该分支永不生效。改为 `useCPUDecode` 为真时跳过 CUDA 探测直接走软解。
- `if (!useCUDA) tempFilters = "hwupload_cuda," + tempFilters`：无条件前置会给**纯 CPU 滤镜链**
  （`scale=...`）插入无效节点而直接失败 → 仅当滤镜链确实含 `_cuda` 时才上传。
- `srcVideoBitrate = ivideo?.bitrate || fileBitrate - 48*1000 || 0`：码率未知时得到 **-48000**，污染
  `videoBitScale` → 加 `Math.max(0, ...)`。
- `--delete-source-files` 的判据仅为 `fs.pathExists`：上次 Ctrl+C 中断残留的
  **0 字节/半截文件同样满足**，会导致「源文件已删、产物却是坏的」的不可逆损失。→ 记录已存在产物的体积，要求
  `> 0` 才允许删源，否则保留源文件并单独告警。
- 新增临时产物注册表 + `SIGINT`/`SIGTERM`/`exit` 清理钩子：此前只在 `try/finally`
  清理，Ctrl+C 时 finally 不执行，`*_tmp@hash@tmp_` 半截文件永久残留。（execa 已用 `cleanup: true`
  负责杀死子进程，这里只负责文件。）
